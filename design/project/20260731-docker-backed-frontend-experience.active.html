体验环境必须走真实后端

mock 可以帮助快速发现界面回归，但只有 Docker 后端能覆盖书籍、封面、登录、阅读与管理等完整链路。

ACTIVE · 已生效 创建日期 2026-07-31 模块 project 需求来源 用户现场指令

原始诉求

“修改界面是可以用 mock 自测，但是用户要求体验，或者启动 dev server 时，必须是基于 Docker 运行后端服务，提供完整全套功能。”

当前规范同时给出了 Docker 与 mock 两种前端启动方法，却没有把“内部自测”和“交付体验”明确分开，容易把只有固定响应的 mock 页面误当成真实产品体验。

两条轨道，不共享终点

MOCK
测试轨
组件测试 隔离 E2E 快速回归
仅限自测

可交付用户

规则落地

允许：mock 隔离自测

界面开发可用 mock 完成组件测试、自动化 E2E 和快速回归。测试服务只对测试过程负责，不得作为体验地址或真实数据验收依据。

强制：Docker 完整体验

用户要求体验，或智能体手动启动并保留 dev server 时，必须先启动 Docker 后端并确认健康，再让 Nuxt 连接 127.0.0.1:8080。

例外边界

自动化测试可以管理短生命周期的 mock 与临时页面服务；它们不得对用户暴露，测试结束后应停止。手动长期运行的 Nuxt 服务不属于此例外。

禁止静默降级

Docker 后端无法启动或健康检查失败时，应报告阻塞和已检查项，不得改用 mock 后端向用户声称“可体验”或“已完成真实验收”。

# 终端 1：Docker 后端
make dev

# 确认真实后端就绪
curl --fail --silent http://127.0.0.1:8080/api/welcome

# 终端 2：Nuxt 连接 Docker 后端
cd app
API_URL=http://127.0.0.1:8080 npx nuxt dev --port 3000 --host 127.0.0.1

影响范围与兼容性

仅修改根目录 AGENTS.md 的前端验收规范，不改变应用代码、Docker Compose、API、测试数据或部署行为。现有 mock 测试能力继续保留，但用途被收窄为隔离自测。

风险与回滚

主要成本是本地体验前需要准备 Docker 镜像和真实数据，但这正是“完整全套功能”可信度的必要条件。若未来需要改变边界，应新建工程治理 WIP 方案说明替代规则；ACTIVE 文档不直接弱化或删除。
