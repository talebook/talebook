同步发布 Talebook GHCR 镜像

在保留 Docker Hub 发布契约的同时，把同一次多架构构建产物推送到 ghcr.io/talebook/talebook，不重复执行耗时的镜像构建。

创建日期：2026-08-13所属模块：project状态：ACTIVE影响范围：GitHub Actions / 镜像发布需求来源：TB-37

1. 原始诉求

“给 talebook 项目增加 ghcr 镜像。”

当前 .github/workflows/build.yml 只登录 Docker Hub，并把 SPA、SSR 和开发镜像发布到 docker.io/talebook/talebook。仓库 workflow 已具有 packages: write 权限，但没有使用 GitHub 提供的令牌发布 GHCR。

2. 目标与边界

类型内容
目标push 与版本 tag 发布时，同步产生 ghcr.io/talebook/talebook 的 SPA、SSR 与 dev 镜像。
目标GHCR 沿用 Docker Hub 的 tag 和多架构集合，用户切换 registry 时无需改变 tag 语义。
保持不变PR 只构建不推送；Docker Hub 主镜像与兼容别名 talebook/calibre-webserver 继续发布。
非目标不迁移或删除 Docker Hub 镜像，不改变 Dockerfile、运行时内容与 Compose 默认镜像。

3. 方案

结论：每个平台的 Buildx action 增加第二个 registry exporter，将相同构建结果按 digest 推送到 Docker Hub 和 GHCR；merge job 再分别从两个 registry 的 digest 创建同构 multi-arch manifest。

  • 增加 GHCR_REGISTRY=ghcr.io，镜像名继续取 github.repository，从而自然得到 ghcr.io/talebook/talebook。
  • build 与 merge job 使用 github.actor 和短期 GITHUB_TOKEN 登录 GHCR，权限限定为现有的 packages: write。
  • SPA、SSR 的单架构产物一次构建、双 registry 输出；manifest 脚本循环 registry，分别引用各自 registry 内的 digest。
  • dev target 仍只在 master push 时发布，但一次为 Docker Hub 与 GHCR 打两个 tag。
  • 把 .github/workflows/build.yml 纳入 Docker 路径过滤，确保发布配置自身变化会触发构建验证。

4. 风险与回滚

  • 首次发布依赖组织允许仓库的 GITHUB_TOKEN 创建或写入 package；真实权限边界需由 GitHub Actions 验证。
  • 双 registry 推送增加上传时间和存储占用，但不会重复运行 Dockerfile 构建阶段。
  • 任一 registry 推送失败会令发布 job 失败，避免两个来源悄然产生不同版本。
  • 回滚可移除 GHCR 登录、第二 exporter、第二 manifest 循环目标和 dev 的 GHCR tag，不涉及镜像内容或数据迁移。
