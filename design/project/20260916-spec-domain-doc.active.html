用 spec/ 建立唯一领域规格文档

把散落在 146 份方案、根级 CONTEXT.md 和代码里的产品定义，收敛成仓库根下唯一一份、无时态、总是最新的领域规格；并用流程条款与机器门禁保证它不退化成第四份过期文档。

状态：ACTIVE 创建日期：2026-09-16 所属模块：project 影响范围：spec/、CONTEXT.md、design/wiki/、AGENTS.md、scripts/、Makefile、tests/ 需求来源：用户要求「重新定义 wiki 内容，作为产品设计主逻辑文档」并要求先 grill

1. 原始诉求

“我想重新定义 wiki 里面的内容，作为 talebook 项目的产品设计主逻辑文档。需要你帮助我进行设计，包括目录层次（比如每个文件应该是个概念实体，比如「书库」、「书籍」、「作者」、「标题」），文件内部描述该实体的所有产品功能（比如包含定义、use-case、术语、功能、界面用词、行为逻辑等）。你先 grill-me 讨论清楚。”

触发背景：上一轮已从 design/ 的 146 份方案与代码中蒸馏出 design/wiki/ 共 16 篇知识库，但那份是贴着代码描述现状的实录文档，带 Status 时态标注，且明确声明「代码 > ACTIVE 方案 > 知识库」。它无法承担产品设计主逻辑的职责。

grill 过程中用户追加确认的关键定性：“他是领域规格文档，并且是唯一一份，总是最新，不存在未实现或者已废弃的情况。”

2. 目标与边界

目标

  • 仓库根下建立 spec/，按领域名词划分实体，每篇统一 7 节骨架。
  • 删除根级 CONTEXT.md 与 design/wiki/，领域定义只有一个归属地。
  • 正文使用产品语言，实现细节集中在每篇末节「实现对照」。
  • 无时态：不写未实现、不写已废弃、不写变更历史。
  • 新增 make check-spec 门禁与 AGENTS.md 流程条款，保证「总是最新」可执行。
  • 不变量：design/ 的方案生命周期门禁与既有写作规范保持不变。

非目标

  • 不改动任何运行时代码、数据库、接口或页面行为。
  • 不迁移 document/ 面向使用者的文档，不处理 docs/ 与 document/ 的历史重复。
  • 不为 design/ 下既有 146 份方案补写或重排。
  • 不把 spec/ 内容对外发布或翻译成英文。
  • 不修正本次发现的三处文档与代码漂移，只记录（见第 4 节）。

本方案不改变用户可感知功能，因此这里替换为仓库内五类文字资产的职责切分。边界能否一句话说清，是本次命名与选址的验收口径。

4. 现状、根因与证据

目录与命名的每一处取舍都以代码或界面文案为证据，不凭语感。

决策证据结论
目录不叫 context/ 而叫 spec/用户定性为「领域规格、唯一一份、代码向它对齐」；context 字面为背景材料名实相符，且与 design/ 的边界能一句话说清
OPDS 归入外部访问而非独立协议篇webserver/plugins/source/opds.py 的 manifest 含 "service_toggle": "opds"，status() 返回 service_enabled；/api/admin/plugins/opds-service 写 OPDS_ENABLED；handlers/opds.py 据此决定对外服务开关对外 OPDS 服务的开关长在插件卡片上，必须写明这处耦合
WebDAV 服务端不归插件管全仓仅 opds.py 一处出现 service_toggle；talebook.source.webdav 只声明 sources.browse / sources.acquire。WebDAV 服务端另有自己的开关 ENABLE_WEBDAV_SERVICE，在 webserver/webdav/handler.py:55 于请求时检查，属管理员设置项而非插件状态；另有 WEBDAV_SYNC_FOLDER 控制每用户可写同步目录两个协议的开关位置不同：OPDS 在插件卡片，WebDAV 在系统设置。WebDAV 服务端不能放进插件目录，否则误导读者以为停用插件会关闭挂载

5. 方案

5.2 每篇骨架

顺序是「先建立直觉，再交付词汇，最后进入细节」：读者先知道这是什么、谁在用、能做什么，此时再看术语表才有上下文，然后带着统一词汇读行为逻辑。

  1. 定义：一句话说清是什么，紧跟「不是什么」的边界。
  2. 使用场景：谁、在什么情况下、要达成什么。
  3. 功能：功能概述清单，一行一条。
  4. 术语与界面用词：术语表（标准用词、英文、含义、示例四列）与操作按钮用词表（界面用词、位置、行为三列）；示例必须是具体的书、作者或读者动作，不用占位描述；不抄文案原文，不写 Avoid 反例。
  5. 行为逻辑：详细产品设计，规则、状态流转、约束与边界情况；全篇最重。
  6. 关联实体：与其他篇的关系与互链。
  7. 实现对照：唯一做「概念到代码位置」映射的地方（正文可自由使用英文术语、协议名与产品自身定义的稳定标识），按落点类型拆成五张子表，每张子表有自己的列头，不适用时整张删除：
    7.1 数据存储（概念、存储、表与字段）、7.2 API 接口（方法、路径、说明）、7.3 关键定义（符号、值、含义——常量、枚举与限额）、7.4 代码落点（行为、文件与函数）、7.5 界面文案（i18n 分组、覆盖范围）。

5.3 命名规则

  • 目录与文件名一律中文；协议专名（OPDS、WebDAV、BRS、TXT）保留原写法。
  • 文件名与文中主术语以领域术语为准；界面用词只出现在第 4 节。
  • 一级标题与文件名严格一致；索引篇例外——它不遵守七节骨架，只需存在、收录每一篇，且指向 spec/ 内文件的链接文案等于目标文件名。

5.4 维护机制

  • AGENTS.md 增加条款：改变产品行为的改动必须在同一 PR 更新 spec/ 对应篇；方案 HTML 声明 spec 影响范围。
  • 新增 scripts/check_spec.py 与 make check-spec，校验：7 节齐全、一级标题与文件名一致、内部互链有效、实现对照节引用的文件路径存在、引用的路由能在 webserver/handlers/ 命中、每个已注册内置插件在 spec/插件/ 下有归属。
  • 机器查不出「行为逻辑变了没改文档」，该部分由流程条款与评审承担。

5.5 交付顺序

  1. 本方案 + spec/元数据.md 与 spec/阅读状态.md 两篇样片，供定调。
  2. 定调后补齐其余 21 篇。
  3. 最后交付门禁脚本与测试、AGENTS.md 条款；同批删除 CONTEXT.md 与 design/wiki/，并回退 check_design_docs.py 的 wiki 豁免与对应测例。
删除动作刻意安排在最后一步：在 spec/ 补齐之前删除 design/wiki/ 会丢失尚未重组的 14 篇内容。

6. 影响范围、风险与回滚

影响范围：新增 spec/ 共 23 篇；删除 CONTEXT.md 与 design/wiki/；新增 scripts/check_spec.py 与测试；修改 Makefile 与 AGENTS.md；删除交付过程中一度为 design/wiki/ 添加的 check_design_docs.py 豁免，使该脚本与其测例回到主干原状（该豁免从未进入主干）。

保持不变：运行时代码、数据库、接口、页面行为、design/ 方案门禁、document/ 与 research/。

  • 主要风险：spec/ 随时间失准，退化为第四份过期文档。缓解：门禁覆盖可机检部分，流程条款覆盖其余，并把「是否更新 spec/」写进方案模板的影响范围。
  • 次要风险：「不写未实现」会让书单等已有设计从文档中消失，新同学可能重复设计。缓解：对应 design/ 方案仍在仓库中，且在第 4 节留痕。
  • 回滚：本次只增删 Markdown、HTML、校验脚本与规范文本，按文件回退即可，无数据迁移。

界面审查：本次无页面、交互、文案资源或前端消费者变化，判断依据为改动仅涉及 spec/、design/、scripts/、tests/、Makefile 与 AGENTS.md，不进入 app/ 与 webserver/ 代码路径，故豁免 interface-review。剩余风险仅为文档准确性。

7.2 一处由本次改动引入的测试不稳定及其修复

首轮全量回归出现 tests/test_network_library.py 的偶发失败。按基线对照确认是本次引入的，而非既有偶发：

  • 基线 origin/master 连跑 4 次全绿；本分支连跑 4 次中 2 次失败。
  • test_network_library.py 单独连跑 5 次全绿；与新增的 test_check_spec.py 组合跑 3 次中 1 次失败。
  • 失败点是 _wait_finished() 的硬编码 5 秒墙钟超时（tests/test_network_library.py:50），它轮询后台线程池中的搜索任务。

根因：新增的门禁用例原本每条都起一个解释器子进程，其中一条还会遍历整个仓库读文件；这些子进程抢占 CPU 与 IO，使紧随其后的后台搜索线程未能在 5 秒内完成。

修复：把校验逻辑改为进程内调用，仅保留一条子进程用例覆盖命令行与退出码契约。用例数与覆盖范围不变，耗时从 2.16s 降到 0.28s。修复后组合跑 6 次、全量跑 4 次全部通过。

未处理的相邻问题：该硬编码墙钟超时对机器负载敏感，是既有测试的脆弱假设。本次按「只动必须动的」原则不修改它，记录在此作为后续独立工作的输入。
