Docker Build Workflow 只在镜像输入变化时运行

为 .github/workflows/build.yml 增加路径过滤，让文档、设计、测试夹具等不进入 Docker 镜像的改动不再触发重型多架构构建；真正影响前端、后端或镜像运行配置的改动仍会构建。

创建日期：2026-08-12 所属模块：project 状态：ACTIVE 需求来源：TB-25 给 docker build actions 增加 filter

1. 原始诉求

“参考 multica 仓库 CI 的做法，增加 filter，只有真正修改前端和后端代码时才触发 docker build workflow，最终达到提效的目的。”

现有 build.yml 在 master、开发分支、Codex/Claude 分支、版本 tag 和 PR 上都会进入 Docker 构建链路。对于只改文档、设计方案或普通测试的提交，这会浪费 Docker Buildx、QEMU 和镜像推送相关 runner 时间。

2. 目标与边界

类型内容
目标PR 和分支 push 只有在 Docker 镜像输入变化时运行 prepare、build、merge 重型链路。
目标保留 tag 发布构建，避免版本发布因为没有可比较路径而被误跳过。
边界不改变镜像 target、tag 规则、Buildx cache、Docker Hub 登录和 manifest 合并逻辑。
非目标不为 ci.yml 的后端或前端测试 job 单独增加过滤；本次只处理 Docker build workflow。

3. 方案

  • 新增轻量 changes job，使用 dorny/paths-filter@v3 输出 docker 布尔结果。
  • push 事件以 github.event.before 作为比较基准，避免开发分支早先的代码改动导致后续文档提交反复触发 Docker 构建；PR 事件仍由 action 使用 PR base 检测。
  • prepare 改为依赖 changes，并只在 needs.changes.outputs.docker == 'true' 时运行；后续 build 和 merge 通过原有 needs 自动跳过。
  • 过滤路径覆盖 Dockerfile 实际复制或依赖的前端、后端、Nginx、Supervisor、启动脚本、requirements、Compose 与 Makefile 输入。
  • tag push 跳过路径检测并直接放行，继续承担发布镜像职责。
会触发 Docker 构建不会触发 Docker 构建
app/**、webserver/**、server.pyREADME.md、document/**、design/**
Dockerfile、.dockerignore、docker/**tests/** 中不进入镜像构建 target 的普通测试变更
conf/nginx/**、conf/supervisor/**、requirements*.txt、docker-compose*.yml、Makefile项目规划、调研、截图和开发说明类文件

4. 风险与回滚

  • 路径列表漏掉真实镜像输入会导致构建被跳过；因此列表按 Dockerfile 的 COPY、依赖安装和运行配置逐项映射，并用单元测试固定。
  • 若未来 Dockerfile 新增复制路径，必须同步更新 filter 和测试。
  • 回滚只需移除 changes job，并恢复 prepare 不带 needs 和 if 的原状。
