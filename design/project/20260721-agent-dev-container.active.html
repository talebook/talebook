1. 原始诉求与已确认决策

完整优化 .github/workflows/claude.yml 与 .github/workflows/codex.yml，使用仓库 Dockerfile 构建具备开发能力的镜像，让 Claude 与 Codex 的实际运行进程都位于该容器中，并保证容器能够完成前后端开发、lint、构建与测试。修改完成后必须使用本地 GitHub Actions 执行验证，全部通过后才允许提交和创建 Pull Request。

已确认：沿用 ci.yml 的 job container 模式；只维护浮动标签 talebook/talebook:dev，不发布 commit SHA 标签。只有 master push 可以覆盖该镜像。实际文件名是 claude.yml，原始诉求中的 claude.yaml 视为同一文件。

本次只改交互式 Claude workflow，不改变独立的 claude-code-review.yml。后者是 PR 自动审查入口，不属于原始诉求点名的两份 workflow；若未来也要迁移，应在本方案生效后另开变更，避免同时改变三条机器人链路。

2. 当前问题

位置当前行为问题
ci.yml后端 job 使用 talebook/talebook-base:latest已证明 job container 能解决 Calibre/Python 系统依赖，但该 base 不含前端与 agent 工具。
Dockerfile dev提供应用开发运行环境并安装 Node 与 app 依赖仍缺 git、jq、pytest、ruff、bubblewrap、Codex CLI 等业务与 agent 工具；无法直接承担 Actions agent job。
claude.yml运行于裸 ubuntu-latest，允许命令范围主要覆盖后端业务环境与仓库 CI 不一致，不能稳定执行前端 lint/build/test；Claude Action 自身的运行时由 Action 管理，不等同于项目依赖。
codex.yml运行时安装 Python 工具、Codex、bubblewrap、AppArmor 配置每次重复安装，步骤长且依赖宿主状态；与本地开发镜像、常规 CI 环境产生漂移。
本地验收单元测试和 actionlint 能检查静态契约缺少用 act 真正在 job container 中执行完整工具链与项目命令的验收入口。

3. Anthropic 与 GitHub 官方调研结论

官方证据结论对本方案的影响
claude-code-action/action.yml @v1 是 composite action；默认在调用 job 中安装固定 Bun、安装 Action 自身依赖并启动 Claude。所有内部 run step 使用 bash。 使用 job container 后，Action 和它启动的 Claude 都在该容器中运行；dev 镜像必须有 bash、curl、CA 证书等基础能力，但无需替 Action 固定 Claude 版本。
官方 Custom Tools 文档 业务命令不会被 Action 自动准备，也默认不能随意执行；仓库应先提供可执行环境，再用 --allowedTools 精确授权 npm、测试等命令。 Talebook 的 Python、Calibre、Node、lint/test 工具放进 dev 镜像；claude.yml 只负责授权已有命令。
官方 custom executable inputs path_to_claude_code_executable 与 path_to_bun_executable 会跳过自动安装；官方警告旧版或不兼容版本可能失败，并说明通常只用于调试或特殊环境。 本方案不设置这两个输入，不把它们误作业务依赖机制；跟随 @v1 自己选择兼容运行时。
官方 custom executables 测试 若确需自定义路径，官方测试会先显式安装并验证 Bun/Claude，再把两个绝对路径同时传给 Action。 证明自定义路径是完整替换机制，不适合只在镜像里随意预装一个 Claude CLI；当前没有采用它的必要。
GitHub job container 文档 jobs.<job_id>.container 会让没有另行指定容器的 job steps 在目标容器中执行；容器内 run step 默认 shell 是 sh，可由 workflow 改成 bash。 这是让 composite Claude Action 使用 Talebook 业务环境的官方 GitHub 机制，与当前 ci.yml 一致。
仓库搜索结果：Anthropic 官方仓库没有提供 container: 或 setup-python 的现成示例，也没有“安装业务依赖”的 Action input。官方示例只通过 --allowedTools 开放 npm/bun 等命令，隐含前提是这些命令已存在于 runner。故 Talebook 应采用 GitHub 官方 job container 负责业务环境，同时保留 Claude Action 的默认运行时管理。

4. 目标与非目标

目标

  • 同一个 dev target 提供 Calibre、Python 生产/测试依赖、Node/npm、常用开发命令、Codex CLI，以及 Claude Action 自动安装自身运行时所需的基础系统能力。
  • build.yml 对 PR 构建该 target，只在 master push 时发布 talebook/talebook:dev。
  • claude.yml 与 codex.yml 使用 jobs.<job>.container.image 消费同一个固定名称的开发镜像。
  • 目标代码 checkout 仍可指向 issue/PR 的目标 SHA；提示模板与 workflow 资源继续来自不可变 workflow SHA，容器环境使用 master 最新成功发布的 dev 镜像。
  • Claude job 在 checkout 后按当前分支执行 make init 与 npm ci；镜像负责系统与语言基线，lockfile 同步负责目标分支依赖准确性。
  • 本地使用 Docker 构建同名镜像，并通过 act 在该容器中真实执行工具检查、后端测试、前端 lint 与构建。

非目标

  • 不改变 Claude/Codex 的触发语法、维护者授权规则、评论格式、Codex 发布门禁与 fast-forward push 规则。
  • 不替换生产镜像，不把测试/agent 工具带入 production stages。
  • 不让 agent 获得 Docker socket、宿主文件系统或特权容器权限。
  • 不在 PR 阶段向 Docker Hub 推送镜像；PR 只验证 dev target 可构建。

5. 总体方案

4.1 Dockerfile

  • dev 从 test stage 继承，使 pytest、ruff 等测试依赖天然存在；production 仍从 server 分叉，不受影响。
  • 显式安装 git、jq、Node.js 20、bubblewrap、uidmap 等 Actions 与 agent 需要的用户态工具。
  • 固定安装 Codex CLI 0.144.6，版本由 Docker build arg 声明并在构建日志中验证；不预装 Claude/Bun，由 claude-code-action@v1 在 job container 内按其官方默认流程管理兼容版本。
  • 保留现有应用开发能力、Nuxt 源码和 npm 依赖。镜像内的依赖服务于其自带应用副本，不能替代 Actions workspace 对当前 checkout 执行 lockfile 同步。

4.2 build.yml 与镜像生命周期

  • PR 的 linux/amd64 构建矩阵额外构建 dev target，不推送。
  • 只有 refs/heads/master 的受信任 push 在 linux/amd64 构建并推送 talebook/talebook:dev；dev、claude、codex 等其他分支不得覆盖它。
  • 镜像写入构建 commit 的 OCI revision label，并在构建日志中记录 digest，保留“当前 dev 来自哪个提交”的排查证据；标签本身按维护者决定保持浮动。
  • Claude/Codex 固定使用 talebook/talebook:dev，目标 PR 无法选择其他运行镜像。镜像拉取失败时 job 在 agent 启动前失败关闭，不回退到 base 或裸 runner。

4.3 Claude workflow

  • 增加 talebook/talebook:dev job container，并把 run shell 统一为 bash。
  • checkout 后先探测 Calibre、Python、Node、make、pytest、ruff 等业务工具，再执行 make init 与 npm --prefix app ci；任何一步失败都不启动 Claude。
  • 不设置 path_to_claude_code_executable 或 path_to_bun_executable；Action 的 composite steps 会在 dev 容器里完成自身运行时准备，避免与浮动 @v1 产生兼容性错配。
  • 允许的开发命令覆盖仓库既有 Makefile、Python/ruff/pytest、npm/npx/node，继续依赖 Action 自身的权限控制，不额外开放宿主资源。

4.4 Codex workflow

  • 增加同一个 talebook/talebook:dev job container，删除 setup-python、pip 安装、npm 全局安装与宿主 AppArmor 改写。
  • 保留启动前的工具版本与 codex sandbox -- /bin/true 自检；开发镜像缺工具或 sandbox 无法创建时直接失败。
  • 预检通过后执行 make init 与 npm --prefix app ci，使当前 checkout 的 lockfile 依赖在恢复模型凭据前就绪；不依赖镜像中其他路径的 node_modules。
  • 容器仅增加 user namespace 所需的 seccomp=unconfined；本机已验证默认容器创建 user namespace 失败，加入该选项后成功。不得使用 --privileged、Docker socket 或 danger-full-access。
  • 保留现有自定义 codex-employee 权限、凭据环境剥离、受信任 prompt/progress reporter、结构化结果门禁和受控发布流程。

6. 信任边界与失败策略

风险控制失败行为
浮动 dev 标签改变内容接受维护者指定的单一 dev 标签；仅 master 可发布，并记录 OCI revision 与 digest拉取失败时 job 不启动；工具自检不通过时 agent 不运行
PR 修改 Dockerfile 注入工具PR 只构建不推送；agent 固定使用 master 最近成功发布的 dev未信任镜像不会被 agent workflow 消费

目标分支依赖变更镜像提供编译器/运行时；Claude 与 Codex job 都在模型凭据可用前按当前 checkout 的 lockfile 同步依赖依赖安装失败时不启动 agent

7. 本地 GitHub Actions 验收

新增一个只负责环境验收的 workflow，生产 agent workflow 与本地 smoke workflow 共享相同的镜像表达式。它不接收 agent 凭据、不发布代码，适合 act 真实执行。

  1. 本地构建 talebook/talebook:dev，覆盖本机同名测试镜像但不推送。
  2. 用 act workflow_dispatch 启动 smoke workflow，禁止拉取同名远端镜像，确保使用刚构建的本地镜像。
  3. 容器内验证 bash、curl、git、jq、Node/npm、Python/pip、make、ruff、pytest、Codex、bubblewrap；Claude/Bun 由 Action 自己安装，不作为业务镜像预装工具断言。
  4. 容器内先执行与 Claude job 相同的 make init 和前端 npm ci，再运行设计检查、Python lint、完整后端 pytest、前端 lint 与 Nuxt build。
  5. 使用 actionlint 和 workflow 契约测试覆盖 claude.yml、codex.yml、build.yml 及 smoke workflow。
边界：本地验收不调用真实 Claude/OpenAI API，不向 GitHub 写评论或推送分支，避免消耗凭据和制造外部副作用。两套真实 agent workflow 的认证/API 阶段由精确契约测试覆盖；共同的容器、工具和项目开发测试由 act 实际运行覆盖。

9. 发布、回滚与实施顺序

  1. 先以测试驱动更新契约，再修改 Dockerfile、build workflow 与两套 agent workflow。
  2. 完成本地 Docker + act + 项目测试；失败时保持 WIP，不提交、不创建 PR。
  3. 验证全部通过后回写本页真实命令、结果与限制，将文件改为 .active.html。
  4. 提交功能分支、推送并创建 PR；PR 构建验证 dev target，但不发布镜像。
  5. 合并到 master 后，build workflow 覆盖发布 talebook/talebook:dev；发布完成前，新 workflow 可能暂时消费旧 dev 并在工具自检处失败，禁止静默回退。

回滚时从最后一个已知正常的 master 提交重新构建并覆盖 talebook/talebook:dev，或回退相关 master 提交后让 build workflow 重新发布。不得从未信任分支手工覆盖 dev；回滚完成后重新运行工具自检与本地 smoke。
