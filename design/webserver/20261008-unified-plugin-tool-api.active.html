插件能力调用统一为 /api/plugins/<key>/exec/<action>

书籍工具、管理端能力测试和额外功能原先各有一套按插件或按能力命名的路由，每加一个工具或能力就要新增 handler 与接口。本方案把所有“对某个插件做一件事”的调用收敛到唯一入口 POST /api/plugins/<plugin_key>/exec/<action>，其余插件接口按平台资源组织，路由表里不出现任何插件名。

状态：ACTIVE 创建日期：2026-10-08 所属模块：webserver 影响范围：webserver/handlers/、webserver/plugins/tool/、app/pages/plugins/、app/components/PluginCapabilityTester.vue、spec/插件/、document/PluginGuide.md 需求来源：Rex 在项目对话中的原话

1. 原始诉求

“优化一下 talebook 项目的插件系统：当前每个插件都要修改handler暴露独立的api接口，这不合理，应该是有统一的restfull的api，不要每新增插件都新增api”
反馈轮（2026-10-19）：“我还是希望用 /api/plugins/<key>/exec/<action> 这种模式，你重新再设计一下，梳理所有plugin接口”

第一轮只把书籍工具收敛为 /api/plugins/<key>/tool[/preview|/run]。反馈轮要求以 exec/<action> 作为统一调用形态，并把全部插件接口一起梳理，因此书籍工具、管理端能力测试和额外功能都迁到同一个入口。

2. 目标与边界

目标

  • 插件接口只有两类：平台资源接口（目录、启停、连接、运行、偏好）和能力调用入口 exec。
  • 对单个插件发起的所有调用走 POST /api/plugins/<key>/exec/<action>，路由表中不出现任何插件名。
  • handler 不认识具体工具：格式优先级、参数白名单、写回方式、新书后缀、元数据同步、超时、审计摘要都由 provider 自述。
  • 新增插件只需实现能力协议并在 register.py 注册；新增一种标准能力调用只在动作表登记，不加路由。
  • 权限不变：工具预览要求登录并逐书校验可见性，工具执行与三类能力测试仅管理员，额外功能受 manifest 声明约束。

非目标

  • 不改连接、五种动作、运行记录等资源接口：它们操作平台对象，按 REST 资源组织更合适。
  • 不改网络书库 /api/book-sources/*、Legado 书源管理与验证码接口：按领域聚合多个书源，不是“对单个插件调用”。
  • 不保留旧路由别名：前后端同仓同版本发布。
  • 不改变工具页、插件中心测试面板和微信读书页的界面与交互。

4. 现状、根因与证据

观察权威证据结论
每个工具都有专属路由原 plugin_booktools.py routes()：text-replace/preview、run；txt-fixer/analyze、run；zh-converter/run；epub-beautify/presets、preview、run新增工具必须新增 handler 与路由
handler 硬编码工具差异原 UserZhConverterRun 的方向、语言后缀与元数据同步；_epub_beautify_input 的 17 个字段工具语义泄漏到 HTTP 层
按能力各开一条测试路由原 /api/admin/plugins/<key>/metadata/search、/source/search、/reviews/lookup，请求体用 query每多一种可测试能力就多一条路由，参数字段名与其他调用不一致
调用形态不统一额外功能走 /features/<action>，工具走 /tool/<action>，能力测试挂在 /api/admin/plugins/ 下同一件事（对插件 X 执行 Y）有三种 URL

5. 方案

方案结论：webserver/handlers/plugin_exec.py 的 PluginExec 是唯一调用入口。带能力前缀的动作查动作表 EXEC_ACTIONS，由平台施加权限后交给对应实现；不带点号的动作交给 manifest extra_features 声明的额外功能；带点号但不在表中的动作返回 plugin.action_not_supported，不会误落到额外功能。
InputPOST …/exec/<action>

请求体 {params, book_id?, output_mode?, suffix?, credentials?}

Guard登录 + 动作权限

动作表声明 admin_only 的动作要求管理员

Dispatch按动作名分发

平台动作查 EXEC_ACTIONS；无点号走 extra_features；其余拒绝

关键决策

决策点选择理由放弃项
调用形态/api/plugins/<key>/exec/<action>用户指定；一个入口覆盖工具、能力测试与额外功能第一轮的 /tool[/action]：只覆盖书籍工具，其余调用仍是另两种 URL
动作命名平台动作带能力前缀（tool.run），额外功能不带点号两类动作命名空间不重叠，平台动作不可能被插件自定义名劫持平铺命名：run 既可能是工具执行也可能是插件自有动作
权限位置动作表声明 admin_only，由 PluginExec 统一施加同一路由下的不同动作需要不同权限，集中在一处便于审查在每个实现里各自判断：容易遗漏
describe 的方法POSTexec 入口只接受 POST，语义是“对插件执行一个动作”exec 同时接受 GET：同一路由两种语义，调用方要记住哪些动作能 GET
参数位置插件参数一律放 params，平台字段在顶层能力测试原来用 query，现与工具、额外功能一致保留 query：同一入口两种参数约定
资源接口保持 REST 资源形态，不并入 exec连接、运行记录是平台对象，有列表、详情、状态，适合资源路由全部塞进 exec：失去资源语义，列表与详情也要变成动作
兼容策略删除旧路由，前端同步迁移前后端同版本发布；保留别名与诉求相悖旧路由转发

6. 影响范围、风险与回滚

影响范围

后端：新增 webserver/handlers/plugin_exec.py；plugin_booktools.py 与 plugins.py 中的工具、能力测试、额外功能 handler 改为动作函数并删除对应路由；webserver/plugins/runtime/interfaces.py 扩展 TransformProvider；webserver/plugins/tool/ 四个 provider 与基类。前端：app/utils/book-tools.ts（pluginExecUrl）、四个工具页、PluginCapabilityTester.vue、pages/plugins/weread.vue、mock server。spec：spec/插件/插件平台.md（5.8 统一接口与 7.2）、元数据源.md、评价源.md、外部书库源.md、微信读书.md、四篇书籍工具的 7.2。开发文档：document/PluginGuide.md。

保持不变

页面界面与交互、权限模型、PluginRun 审计、覆盖写回的备份与回滚、数据库结构、manifest 字段集合、资源接口、网络书库接口。

主要风险：外部脚本直接调用旧路由（/api/plugins/tools/<tool>/*、/api/admin/plugins/<key>/metadata/search 等、/features/<action>）会失效，能力测试的请求体字段从 query 改为 params → PR 与发布说明列出新旧对照。
回滚：整体回退本次提交即可，无数据迁移与配置变更。

8. 决策记录

  1. 2026-10-08：需求未说明范围，第一轮默认只收敛“每插件一套接口”的书籍工具，采用 /api/plugins/<key>/tool[/action]。
  2. 2026-10-08：繁简转换页面上的「保留备份」勾选框此前后端就不读取（写回原书始终备份），维持界面不变，只是不再随请求发送。
  3. 2026-10-19：Rex 指定统一调用形态为 /api/plugins/<key>/exec/<action> 并要求梳理全部插件接口。本方案在同一份文档内迭代：工具的 /tool* 路由、三条管理端能力测试路由和 /features/ 逃生舱全部并入 exec；资源接口与网络书库接口不在 exec 范围内（理由见关键决策）。
