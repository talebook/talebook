TaleAgent 会话聚合模型

统一产品、API 与代码命名，并将逐消息表合并为一个会话 JSON 记录，减少会话持久化实体。

状态：ACTIVE创建日期：2026-08-19所属模块：webserver / app需求来源：TB-62 评论 40998205

1. 原始诉求

成员要求：“名称应该是 TaleAgent。ProtagonistMessage 和 ProtagonistConversation 这两个做一下整合吧，单次对话直接以大 JSON 格式打包进去一个字段里。只保留一个 TaleAgentConversation 作为每次对话的保存记录。”

2. 目标与边界

目标边界
  • 产品名、页面、API、schema、服务与模型统一使用 TaleAgent。
  • 保留 TaleAgent 与 TaleAgentConversation，删除独立消息模型。
  • 一个会话行的单一 JSON 字段保存全部消息、终态、反馈、运行时和错误信息。
  • 继续支持流式、取消、重试、反馈、ACL、级联删除和目录 manifest。
  • 不改变人物思维提炼的产品目标。
  • 不提供旧 Protagonist API 或旧草稿数据库迁移；PR 尚未合并，无生产数据。
  • 单会话只允许一个生成中消息，避免 JSON 并发覆盖。

3. 数据与运行流程

创建会话插入一条 TaleAgentConversation，JSON 初始为空。
发送消息把完整消息对象追加到 JSON 数组并提交。
运行时更新按 conversation id + message id 定位并替换 JSON 中的消息快照。
读取/删除整包返回消息；取消活动任务后删除一条会话记录。

模型

TaleAgent
  id / owner / book / manifest index ...

TaleAgentConversation
  id / tale_agent_id / owner / boundary index ...
  messages = { "items": [
    { "id", "user_content", "assistant_content", "status",
      "feedback", "runtime", "usage", "error", "timestamps" }
  ] }

每次深层更新都复制完整 JSON 并重新赋值，确保 SQLAlchemy 能检测变更。消息对象不包含书籍正文或运行时 prompt。

4. 风险与控制

风险控制
并发更新导致 JSON 丢失同一会话存在 queued/running 消息时拒绝新消息；后台每次从数据库重新加载最新 JSON 后替换目标项。
大 JSON 持续增长首版保持现有产品能力并限制单条输入/输出；测试多轮历史与整包序列化，后续达到容量阈值再单独设计归档。
消息定位性能消息 id 只在创建者已授权的会话 JSON 中扫描；每个会话为有限多轮，不建设冗余消息索引表。
命名遗漏静态测试覆盖模型、表、路由、页面、i18n 和源码中不再存在本功能的 Protagonist 命名。
