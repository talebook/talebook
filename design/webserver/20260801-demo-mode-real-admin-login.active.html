演示模式：真实管理员账号登录维护

在“单账号只读演示模式”基础上，让数据库中标记为真实管理员（admin=True）的账号也能在演示模式下登录，并保留完整读写权限，用于日常维护公开演示站；配置的只读演示账号行为不变。

状态：ACTIVE 创建日期：2026-08-01 所属模块：webserver 影响范围：登录鉴权、演示模式策略、请求只读拦截、副作用记录 需求来源：PR #887 评论 @hehetoshang（2026-08-01）

原始诉求

PR #887（Issue #886 的实现）评论区中，@hehetoshang 在得知“开启演示模式后管理员账号无法登录”是设计如此后，提出：

“那我要怎么维护demo？给我管理员账号允许登录”

拆解为两个可验证的行为点：① 真实管理员账号在演示模式开启时仍能正常登录，登录态不会像其它账号一样被强制视为未登录；② 登录后的管理员拥有与演示模式关闭时一致的读写能力，能够上传/编辑书籍、管理用户、保存真实的后台设置等，以便持续维护演示站内容。

与既有方案的关系

本方案建立在已生效的 design/webserver/20260801-demo-mode-auto-account-fake-admin.active.html（自动开户与伪管理员面板）之上，两者面向不同账号，互不冲突：

既有方案覆盖的账号

  • 配置的 DEMO_USERNAME 只读演示账号：自动开户、只读、假保存、伪管理员设置视图。
  • 其余任何非管理员账号：一律无法登录（demo.account_only）。
+

本方案新增覆盖的账号

  • 数据库 admin=True 的真实管理员账号：可正常登录，会话不再被演示模式强制清空。
  • 登录后不受只读策略限制，写请求与副作用记录（登录 IP、消息、阅读历史、书源权重等）均按非演示模式的正常逻辑执行。

演示账号自身的只读、假保存、伪管理员视图，以及 WebDAV 只读、社交登录禁用等既有设计完全不变，本方案不重复描述，也不需要将既有方案标记为 SUPERSEDED——两者是并列的“账号类型判定”，不存在互相推翻的目标或非目标。

目标与非目标

目标

  • 演示模式开启后，数据库中 admin=True 的账号仍可使用自己的用户名密码正常登录（SignIn、HTTP Basic Auth 均适用）。
  • 该管理员账号登录后的会话在后续请求中持续有效，不会被 get_current_user() 因“不是配置的演示账号”而强制视为未登录。
  • 该管理员账号发起的写请求（POST/PUT/DELETE 等）不再被演示模式的只读策略统一拒绝为 demo.read_only，/api/admin/* 等既有 @is_admin 接口按原有权限模型正常工作，无需为演示模式单独改造。
  • 该管理员账号触发的既有副作用记录（登录 IP/时间、站内消息、阅读历史、图书访问计数、书源搜索权重）按非演示模式的正常逻辑执行，而不是被静默跳过。

非目标

  • 不新增“管理员专用密码”或任何新配置项；账号本身仍需部署者预先创建并设置 admin=True，密码走既有账号体系，与演示模式无关。
  • 不改变配置的 DEMO_USERNAME 只读账号的任何行为，也不允许普通（非管理员）账号登录。
  • 不放开 WebDAV 写操作：WebDAVHandler.prepare() 在演示模式下对所有账号（含真实管理员）统一只读，管理员如需上传/整理书籍文件，走站内网页管理后台而非 WebDAV 同步；WebDAV Basic Auth 允许真实管理员通过身份校验，但方法级别的只读限制不因账号而放开，避免在完整解析 WebDAV Basic Auth 身份之前就需要重构 prepare() 的执行顺序，扩大改动面和出错风险。
  • 不放开社交账号登录：/auth/login/*、/auth/complete/* 等在演示模式下仍统一 403，管理员需使用用户名密码登录。
  • 不在管理后台提供“开启/关闭演示模式”的开关，仍只能通过配置文件控制。

方案

1. 统一的账号判定：demo_mode.is_real_admin() / is_demo_restricted()

webserver/demo_mode.py 新增 is_real_admin(user)：仅当 user.is_admin()（数据库 admin 字段）为真时返回 True，与配置的演示账号判定（is_demo_user）完全独立。在此基础上新增 is_demo_restricted(conf, user)：演示模式关闭时恒为 False；演示模式开启时，仅当该用户不是真实管理员才为 True。这个判定取代了原来分散在各处的 demo_mode.is_demo_mode(CONF) 布尔检查，成为“该请求是否要套用演示只读/伪造限制”的唯一入口。

2. 登录放行：can_login() 增加真实管理员分支

can_login(conf, user) 由 not is_demo_mode(conf) or is_demo_user(conf, user) 扩展为再加一个 or is_real_admin(user)。这一处改动同时覆盖了 SignIn.post()、Done.get()（社交登录回调）、BaseHandler.process_auth_header()（HTTP Basic Auth）与 webdav/auth.py 的登录判定，四处调用点无需分别修改。

3. 会话保持：get_current_user() 复用 can_login()

BaseHandler.get_current_user() 原先的强制登出条件 is_demo_mode(CONF) and not is_demo_user(CONF, user) 改写为 not can_login(CONF, user)：语义上“不允许登录的账号，也不允许维持已登录状态”，与登录判定保持一致；真实管理员账号因 can_login() 已放行而不再被清空会话，self.admin_user 会按既有逻辑基于 user.is_admin() 正常置位。

4. 只读策略放行：request_is_allowed() 接收当前用户

request_is_allowed(conf, method, path, user=None) 新增 user 形参，函数体首行由 if not is_demo_mode(conf): return True 改为 if not is_demo_restricted(conf, user): return True——真实管理员的任意方法、任意路径都直接放行，不再逐条匹配只读方法或白名单路径。调用方 BaseHandler.should_allow_demo_request() 相应传入 self.current_user。

5. 副作用记录：按账号类型决定是否跳过

BaseHandler 中原先无条件跳过的登录 IP/时间记录（login_user）、站内消息写入/清空（add_msg/pop_messages）、阅读历史（user_history）、图书访问计数（count_increase），以及 network_library.py 里的书源搜索权重更新，判定条件统一由 demo_mode.is_demo_mode(CONF) 改为 demo_mode.is_demo_restricted(CONF, user)（或 self.current_user）。真实管理员的这些操作恢复正常记录，演示账号与匿名访客不受影响，继续跳过。

SignIn.post() 里的密码格式迁移（SHA256 → bcrypt）同样由 is_demo_restricted() 判定，真实管理员登录时按需完成迁移，演示账号仍保持不迁移。

6. 管理后台接口无需任何改动

webserver/handlers/admin.py 中的 @is_admin 装饰器与散落的 if not self.admin_user 判断均依赖 self.admin_user，该属性完全由 BaseHandler.get_current_user() 依据 user.is_admin() 置位。第 3、4 步生效后，真实管理员的会话与写请求都不再被演示模式拦截，self.admin_user 自然被正确设置，因此用户管理、批量删除、书源管理等所有既有管理接口在演示模式下对真实管理员“开箱即用”，本方案不需要修改 admin.py。AdminSettings.is_demo_fake_admin() 只判断“是否为配置的演示账号”，真实管理员始终为 False，因此继续走真实保存路径，与既有伪管理员面板逻辑互不干扰。

安全边界与风险

  • 放行条件严格锚定数据库字段：唯一放行依据是 Reader.admin（现有模型字段），不新增角色、不新增“演示管理员”白名单，避免引入新的权限判定分支需要额外维护。
  • 演示只读账号边界不变：is_real_admin() 与 is_demo_user() 相互独立，演示账号即使被误配置为管理员用户名也不会因为本方案获得额外能力（其能力仍完全由 is_demo_fake_admin() 的伪造视图决定，不受本方案影响）。
  • 公开演示站需要部署者自行保护管理员密码：演示模式开启后，管理员账号的用户名密码即成为整站真实写权限的唯一门槛，与关闭演示模式时完全一致，本方案不降低也不提高这一固有风险；README 已说明管理员账号密码由部署者管理，不受演示模式影响。
  • WebDAV 写操作刻意不放开：如第 4 节所述，WebDAVHandler.prepare() 的只读检查发生在完整解析请求者身份之前，要按账号类型放行需要提前完成 Basic Auth 校验，改动面明显更大；本方案将其列为非目标，管理员改用网页后台维护，风险和实现成本更低。

决策记录

  1. 2026-08-01：放行条件选择“数据库 admin=True”而非新增独立配置项，理由是部署者已经在用这个字段管理真实管理员，复用既有语义、无需额外配置即可生效，也不需要文档额外说明一个新概念。
