演示模式：访客权限对齐与用户管理页操作锁定

在“单账号只读演示模式”基础上补齐两处细节：① 未登录访客与配置的演示账号在阅读/下载书籍时统一遵循后台“访客权限”设置，不再让演示账号沿用自身默认拥有的完整权限位；② 用户管理页在演示模式下将演示账号所在行的操作按钮替换为锁定提示，避免公开演示站的访问者在自己账号视角看到可点击但实际不生效的管理入口。

状态：ACTIVE 创建日期：2026-08-01 所属模块：webserver 影响范围：webserver 阅读/下载权限判定、AdminUsers 接口返回字段；app 用户管理页操作列 需求来源：PR #887 评论 @hehetoshang（2026-08-01 07:12）

原始诉求

PR #887（Issue #886 的实现）评论区中，@hehetoshang 提出：

“我希望演示模式时，在用户管理中，演示用户的操作按钮直接被隐藏，只有退出demo模式时或者不是演示用户时才显示，然后演示模式的未登录与演示用户的权限要遵循访客权限设置的”

拆解为两个可验证的行为点：① 用户管理页表格中，演示账号所在行的“操作”按钮仅在演示模式关闭、或该行不是演示账号时显示；② 演示模式下，未登录访客与演示账号的阅读/下载等能力统一由 ALLOW_GUEST_READ/ALLOW_GUEST_DOWNLOAD/ALLOW_GUEST_PUSH/ALLOW_GUEST_UPLOAD 决定，而不是沿用演示账号自身的权限位（该账号自动创建时未设置 permission，按 has_permission() 的默认值等同于拥有全部权限）。

与既有方案的关系

本方案建立在已生效的 20260801-demo-mode-auto-account-fake-admin.active.html 与 20260801-demo-mode-real-admin-login.active.html 之上，复用 webserver/demo_mode.py 中已有的 is_demo_restricted(conf, user) 判定（演示模式开启且非真实管理员时为 True），不引入新的账号类型判定分支，也不改变真实管理员账号的既有行为——真实管理员在阅读/下载等场景下继续使用自己账号的权限位，与演示模式无关。

目标与非目标

目标

  • 演示模式下，在线阅读（/read/<id>）、EPUB 分页读取（/get/extract/<id>/...）、书籍下载（/api/book/<id>.<fmt>）三个只读入口，对未登录访客与配置的演示账号统一按 ALLOW_GUEST_READ / ALLOW_GUEST_DOWNLOAD 判定，忽略演示账号自身的 can_read()/can_save() 权限位。
  • 真实管理员账号不受影响：即使 ALLOW_GUEST_READ/ALLOW_GUEST_DOWNLOAD 关闭，真实管理员仍按自己账号的权限位正常阅读/下载。
  • GET /api/admin/users 返回的每个用户对象携带 is_demo 字段，标记该账号是否为当前配置的演示账号。
  • 用户管理页（app/pages/admin/users.vue）在 sys.demo_mode 为真且该行 item.is_demo 为真时，将“操作”下拉按钮替换为一段说明文字；演示模式关闭或该行不是演示账号时，操作按钮保持原有下拉菜单。

非目标

  • 不改变推送（BookSendToDevice/BookSendToMail）与上传（BookUploadBase）两类接口的代码路径：这两者都是 POST 请求，在演示模式下已被 demo_mode.request_is_allowed() 的只读白名单统一拦截为 demo.read_only（配置的演示账号无法到达业务代码），本方案不重复处理，只在“行为矩阵”中说明现状。
  • 不在用户管理页新增“为什么被锁定”的详情弹窗或帮助链接，仅以行内文字说明，与既有该页面其它状态提示（如“已停用”“待激活”）的呈现方式保持一致的克制程度。
  • 不改变 is_demo 字段以外的用户列表字段与排序、分页逻辑。
  • 不新增独立的“演示模式访客权限”配置项，仍复用已有的 ALLOW_GUEST_* 四项配置。

方案

1. 阅读 / 下载：以 is_demo_restricted() 决定是否套用访客权限

在 webserver/handlers/book.py（BookDownload.prepare、BookRead.get，含其中的 PDF 分支）与 webserver/handlers/files.py（EpubReader.get）三处权限判断前，统一计算：

guest_like = not self.current_user or demo_mode.is_demo_restricted(CONF, self.current_user)

该表达式在四种组合下的取值：演示模式关闭 + 匿名 → True（与改动前行为一致，走原有“匿名访客”分支）；演示模式关闭 + 已登录 → False（继续用账号自身权限位，未变）；演示模式开启 + 匿名或演示账号 → True（新增：演示账号被并入“访客”分支）；演示模式开启 + 真实管理员 → False（继续用账号自身权限位，不受影响）。guest_like 为 True 时只检查对应的 ALLOW_GUEST_* 布尔值，不再检查 is_active()/can_read()/can_save()——访客本就没有“账号状态”的概念。

2. 用户列表：AdminUsers.get() 标记 is_demo

webserver/handlers/admin.py 的 AdminUsers.get() 在拼装每个用户的返回字典时，新增一行 "is_demo": demo_mode.is_demo_user(CONF, user)，复用既有的用户名比对逻辑，不查询演示模式是否开启（是否需要“锁定展示”由前端结合 sys.demo_mode 一并判断，接口本身只回答“这是不是那个账号”）。

3. 用户管理页：锁定态的视觉与信息层级

沿用页面既有的 Vuetify Material 视觉语言（不引入新配色体系），只对“操作”单元格的内容做条件切换，信息层级遵循“状态优先于操作”：当一行处于锁定态时，用户第一眼看到的应是“为什么没有按钮”，而不是一个禁用态的按钮引诱去点击。

用户名邮箱登录时间操作
alice_adminalice@example.com2026-08-01 10:02 操作 ▾
demodemo@talebook.demo2026-08-01 09:58 演示模式下该账号操作已锁定

锁定行以浅紫底色与左侧圆点弱化区分，文字为次要文本色（text-medium-emphasis），不使用红色/警告色——这不是一个错误状态，而是演示站点的正常边界，不应带给管理员“出错了”的紧张感。

实现上，#item.actions 插槽在 store.sys.demo_mode && item.is_demo 为真时渲染提示 <span>，否则保留原有 <v-menu> 结构与其中的权限开关、激活账号、设为管理员、删除用户等既有能力，互不影响。文案通过 i18n key admin.users.label.demoAccountLocked 提供中英文案。

安全边界与风险

  • 用户管理页的锁定是展示层面的引导，不是权限边界：真正阻止修改演示账号的仍是后端——演示账号的写请求本就被 demo_mode.request_is_allowed() 统一拒绝为 demo.read_only；隐藏按钮只是避免管理员误以为点击会生效，属于体验优化而非新增的安全控制，因此不必担心前端被绕过后出现权限漏洞。
  • 访客权限判定不影响真实管理员：guest_like 表达式在真实管理员场景下恒为 False，不会出现“管理员因为访客权限关闭而读不了书”的回归。
  • 推送/上传维持现状是刻意选择而非遗漏：这两类接口已经在更上层被只读策略拦截，若在业务代码里再叠加一层 guest_like 判断，属于死代码，不写比写更清楚。

决策记录

  1. 2026-08-01：推送/上传接口不重复添加 guest_like 判断，理由是这两类接口在演示模式下已经先被只读策略拦截为 demo.read_only，重复判断是死代码；如果未来只读白名单扩大到包含这些路径，应在那次改动里一并处理。
  2. 2026-08-01：用户管理页的锁定态使用文字说明而非置灰按钮，理由是置灰按钮仍然会引诱点击并让用户困惑“为什么按下去没反应”，直接替换为说明文字更符合“错误与空态应给出方向而非制造疑惑”的文案原则。
  3. 2026-08-01：is_demo 判定放在后端而不是前端用用户名字符串比较，理由是演示账号用户名（DEMO_USERNAME）是后端配置，前端不应假设或硬编码该值，也避免配置变更后前后端不一致。
