用类型化能力接口取代单一 execute

插件不再只暴露一个 execute(context)，而是按元数据、笔记、评价、书源、格式转换等能力实现各自的类型化接口；业务流按能力遍历插件，通用运行时不再认识任何具体插件。

1. 原始诉求

“当前分支对比 master，实现了插件中心的功能。我需要你审查一下代码架构设计，尤其是 plugin 的协议、hook 是否合理，单个插件是否足够内聚。我感觉是大量 plugin 名称 hardcode 到了各个地方。”

“PluginProvider 的设计太有问题了！元数据、划线笔记、评分、评价、书籍列表，这些都应该明确定义在 PluginProvider 里面，然后在业务流里调用。比如，拉取 meta 信息时，就 for p in plugins.filter(has_meta_hook): p.search_books ...”

会话内已确认的决策

决策结论

2. 目标与边界

目标

  • 通用运行时不再出现任何具体插件的名称、模块或实体分支。
  • 业务流按能力遍历插件获取数据，不再按 plugin_key 硬编码查安装与连接。
  • capabilities 与 download_mode 成为承重声明，与实现不一致时在进程启动期报错。
  • 凭据解密只发生在运行时调用边界内，业务 handler 不再接触密文或明文凭据。
  • 保留现有底座能力：连接租约、退避重试、逐项失败、来源记录幂等、带本地修改保护的回滚。

非目标

  • 不实现插件市场、签名分发或 Web 进程动态 import 用户代码。
  • 不实现 runtime_kind 的 http / managed_process 进程外执行。
  • 不迁移 plugins/captcha/ 与 plugins/parser/，二者不属于用户可安装的扩展能力。
  • 不改动 Calibre 主库结构，也不改动已有的书籍、笔记业务表结构。
验收目标：在 webserver/services/plugin_runtime.py 与 webserver/handlers/book.py 中， grep -c "talebook\.\|weread" 结果为 0；新增一个 annotations 插件无需修改运行时任何一行代码即可正确落库。

4. 接口设计

方案结论：所有权按“谁懂这个数据谁定义它”划分——领域类型由平台定义，取数由插件实现，落库由平台按类型派发。插件不再决定数据如何进入 Talebook 的表，平台不再需要知道数据来自哪个插件。

4.1 三层命名

supports_auto_trigger=False 的插件，其 config_schema 不包含 auto 选项，前端也不渲染该开关——避免让用户配出一个平台会拒绝执行的组合。

4.4 ExtraFeatureProvider 与它的约束

通用 action 入口不是错的设计，错的是它当了唯一接口。现在它退回第 7 个接口，专门装标准化不了的东西——插件自带的、只有其工作台界面懂的功能。方法名采用 execute_feature；旧的 PluginProvider.execute(context) 与 PluginProvider 类型整体废弃，不再作为注册或运行兜底。

class ExtraFeatureProvider(Protocol):
    def execute_feature(self, action: str, params: dict, ctx: PluginContext) -> dict: ...

# manifest 声明白名单，平台按 schema 校验参数
"extra_features": {
    "statistics":         {"mode": "read", "schema": {...}},
    "popular_highlights": {"mode": "read", "schema": {...}},
    "underline_stats":    {"mode": "read", "schema": {...}},
}

# 单条通用路由取代所有插件专属查询路由
POST /api/plugins/{plugin_key}/features/{action}
必须设的约束，否则逃生舱会变成绕过类型系统的万能后门：
  1. 返回裸 dict 只允许出现在这一个接口，其余六个必须返回领域类型。
  2. 能映射到标准接口的必须映射。评审判据：如果一个 action 返回的东西本质上是书、笔记、评分、书源条目之一，它就不该在 extra_features 里。
按此判据，微信读书 11 个 operation 中只有 3 个够格留在 extra。

4.5 capabilities 成为承重声明

CAPABILITY_INTERFACES = {
    "metadata.lookup":     MetadataProvider,
    "annotations.import":  AnnotationProvider,
    "reviews.import":      ReviewProvider,
    "book_sources.search": SourceProvider,
    "book_sources.browse": SourceProvider,
    "integrations.tool":   TransformProvider,      # 三个文本工具同属一个能力：都是对 book content 做处理
    "push.device":         PushProvider,
}

def register(self, plugin):
    manifest = PluginManifest.validate(plugin.manifest)
    for cap in manifest.raw["capabilities"]:
        iface = CAPABILITY_INTERFACES.get(cap)
        if iface is None:
            raise TypeError("%s 声明了平台未知能力 %s" % (plugin, cap))
        if not isinstance(plugin, iface):
            raise TypeError("%s 声明了 %s 但未实现 %s" % (plugin, cap, iface.__name__))

声明了却没实现、声明了平台未知能力，或声明 extra_features 却未实现 ExtraFeatureProvider → 进程启动即失败；实现了却没声明 → 平台不会调用它。capabilities 从装饰字段变为承重字段，同时解决 F-5 与 F-8。

capability 不做过度切分：原有 integrations.content_edit / content_convert / encoding_fix 三个能力串合并为一个 integrations.tool。三者都是对书籍正文做处理，形状相同、权限相同、UI 分组相同，切成三份只增加维护成本而不携带任何平台可用的信息。

5. 书源接口（按 Legado 与微信读书实测签名校准）

书源是能力面最宽的一类。接口按功能最完整的 Legado 校准，再回套 OPDS，反向做一定会漏。

5.2 接口

DownloadMode = Literal["single_book", "by_chapters", "none"]

class SourceProvider(Protocol):
    download_mode: DownloadMode      # 由 manifest 声明，register 期按模式校验方法

    # 找书
    def search(self, query: str, cursor: Cursor, ctx) -> Page[SourceBook]: ...           # read
    def browse(self, category_id: str, cursor: Cursor, ctx) -> Page[SourceBook]: ...     # read
    def get_categories(self, ctx) -> list[Category]: ...                                 # read
    # 详情（必需）
    def get_book(self, external_id: str, ctx) -> SourceBookDetail: ...                   # read
    # download_mode == "single_book"
    def download(self, book: SourceBookDetail, ctx) -> BookFile: ...                     # read（只取回字节，入库由平台负责）
    # download_mode == "by_chapters"
    def get_toc(self, book: SourceBookDetail, ctx) -> list[SourceChapter]: ...           # read
    def get_chapter(self, chapter: SourceChapter, ctx) -> SourceContent: ...             # read
    # 运维
    def self_check(self, ctx) -> CheckReport: ...                                        # read
三处按实测修正：
  • get_toc 收 SourceBookDetail 而非 external_id——否则插件内部要为拿 toc_url 再发一次 book_info 请求。平台在 download_book 中本就先调 get_book()，detail 顺传零成本。
  • get_chapter 收 SourceChapter 而非 chapter_id——Legado 的 content() 吃的是 ch.url。
  • Category.id 与 external_id 必须是完全不透明的字符串。Legado 用 URL 作 identity，平台不得解析、拼接或当整数使用。

6. 运行时与调用模式

6.1 read / write / sync 三种模式

判据是插件行为的副作用方向，不是平台拿到结果后做什么。平台把读来的数据落库，那是平台的编排，与插件方法的模式无关。

维度readwritesync
方向外部 → 平台平台内部（改书）平台 → 外部
插件做什么取数并返回，无副作用修改本地书籍正文把本地数据写进外部服务
典型方法search_books / list_annotations / download / get_chapterTransformProvider.applypush_annotation / PushProvider.push
所需 scope*.readbooks.write*.sync
必须审计 run是是是
幂等要求无按备份恢复必须，避免重复推送
回滚不适用文件备份恢复可能不可用，外部服务未必支持删除
此处修正了先前的错误定义。早先把模式判据定为“是否修改 Talebook 的数据”，据此把 list_annotations 与 download 划为 write。这是错的：插件只是从远端读，写库的是平台。 按修正后的判据，download 只负责取回字节，取回之后如何入库是上层业务逻辑的事，与插件无关，因此是 read； 真正的 write 只有修改书籍正文这一类，目前仅 TransformProvider.apply。
模式决定权限与安全约束，不决定平台编排。 平台调 list_annotations（read）时由 typed runtime 创建能力调用 PluginRun；把结果落库时再由平台摄入流程维护来源记录与游标，两层职责互不替代。 模式回答的是三个问题：需要哪种 scope、是否必须留审计、失败后能否回滚。
顺带收口的安全问题：三种模式与 permissions 已有的 books.read / books.write 词汇同轴，运行时可在派发前强制校验 scope。当前 context["scopes"] 只是传给插件、指望其自觉，执行期从不检查。

6.1.1 sync 模式：外部回写

协议此前只能单向摄入。新增 sync 后，插件可以把 Talebook 的数据写回外部服务，典型场景是把用户在 Talebook 里做的划线笔记回写到 BRS。

class AnnotationProvider(Protocol):
    def list_annotations(self, ctx) -> Page[Annotation]: ...                       # read
    def push_annotation(self, item: Annotation, state: SourceState, ctx) -> PushReceipt: ...  # sync

@dataclass(frozen=True)
class PushReceipt:
    source_annotation_id: str = ""
    source_position: str = ""
    source_raw_hash: str = ""
    source_updated_at: str = ""
这不是从零设计：webserver/services/annotation_sync.py 已经实现了完整的扇出机制—— register_writer(source_name, writer, source_connection_id) 注册钩子、 AnnotationSource 表记录每个来源的 pending / synced / failed 状态与错误、 exclude_source_name 防止回写给数据来源本身造成回环。 但生产代码中没有任何一处调用 register_writer，只有测试注册过（tests/test_annotations.py:310-311）——因为协议里没有 sync 接口，插件无从注册。

本方案把这套机制接入协议：平台在连接启用时，自动为每个实现了 push_annotation 的插件连接注册 writer，register_writer 从公开 API 降为内部实现细节。现有 writer 签名 writer(annotation_dict, source_dict) -> dict 正是 push_annotation 的弱类型版本，返回的四个字段直接对应 PushReceipt。

sync 特有的风险：外部写入通常不可回滚。rollback 对 sync 只能做到“标记来源记录为已撤销并尝试调用插件的删除接口”，插件不支持删除时必须把该项记为 conflict 而非静默成功。回环防护必须保留：从某来源导入的笔记不得再回写给该来源。

按依赖关系排序，不按严重度。第 1 步为纯增量、无兼容性风险，且立即消掉三条路由。

S4 协议收口

S5 解耦落库
