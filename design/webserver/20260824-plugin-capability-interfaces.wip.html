用类型化能力接口取代单一 execute

插件不再只暴露一个 execute(context)，而是按元数据、笔记、评价、书源、格式转换等能力实现各自的类型化接口；业务流按能力遍历插件，通用运行时不再认识任何具体插件。

状态：WIP 创建日期：2026-08-24 所属模块：webserver 影响范围：webserver/plugins/ · webserver/services/ · webserver/handlers/ · app/pages/admin/plugins/ · app/pages/plugins/ 需求来源：feat/plugins 分支架构审查（会话内提出）

1. 原始诉求

“当前分支对比 master，实现了插件中心的功能。我需要你审查一下代码架构设计，尤其是 plugin 的协议、hook 是否合理，单个插件是否足够内聚。我感觉是大量 plugin 名称 hardcode 到了各个地方。”

“PluginProvider 的设计太有问题了！元数据、划线笔记、评分、评价、书籍列表，这些都应该明确定义在 PluginProvider 里面，然后在业务流里调用。比如，拉取 meta 信息时，就 for p in plugins.filter(has_meta_hook): p.search_books ...”

会话内已确认的决策

决策结论
命名分层能力接口 XxxProvider（Protocol）／共享实现基类 XxxBase／具体插件 XxxPlugin
调用模式命名用 read / write，不用 query / sync
格式转换接口名TransformProvider，不用 BookTransformProvider
插件专属功能ExtraFeatureProvider.execute(action, params)，不用 RawQueryProvider
书源接口组织单一胖接口 + 可选方法，不拆多个 Protocol
取书方式声明manifest 声明 download_mode（single_book / by_chapters / none），外层按模式分派
取书方法名download / get_toc / get_chapter，不用 acquire

2. 目标与边界

目标

  • 通用运行时不再出现任何具体插件的名称、模块或实体分支。
  • 业务流按能力遍历插件获取数据，不再按 plugin_key 硬编码查安装与连接。
  • capabilities 与 download_mode 成为承重声明，与实现不一致时在进程启动期报错。
  • 凭据解密只发生在运行时调用边界内，业务 handler 不再接触密文或明文凭据。
  • 保留现有底座能力：连接租约、退避重试、逐项失败、来源记录幂等、带本地修改保护的回滚。

非目标

  • 不实现插件市场、签名分发或 Web 进程动态 import 用户代码。
  • 不实现 runtime_kind 的 http / managed_process 进程外执行。
  • 不迁移 plugins/captcha/ 与 plugins/parser/，二者不属于用户可安装的扩展能力。
  • 不改动 Calibre 主库结构，也不改动已有的书籍、笔记业务表结构。
验收目标：在 webserver/services/plugin_runtime.py 与 webserver/handlers/book.py 中， grep -c "talebook\.\|weread" 结果为 0；新增一个 annotations 插件无需修改运行时任何一行代码即可正确落库。

3. 现状、根因与证据

3.1 根因：契约无类型，所以泛化无从谈起

ProviderItem.data 是无类型 dict，运行时拿到它无法解释，只能靠 entity_type 字符串猜；而“怎么解释”的知识只存在于唯一的生产者里，于是通用运行时直接 import 了那个插件的模块。

书源条目_normalize()，13 个关键字参数，含格式白名单与 ISBN 清洗plugins/runtime/book_sources.py:87

关键判断：前两个已经是写成 dict 构造器的 dataclass，字段名、默认值与校验逻辑都在，唯独没有类型。本方案主要工作是把它们原地升格，而非新造抽象。

4. 接口设计

方案结论：所有权按“谁懂这个数据谁定义它”划分——领域类型由平台定义，取数由插件实现，落库由平台按类型派发。插件不再决定数据如何进入 Talebook 的表，平台不再需要知道数据来自哪个插件。

4.1 三层命名

层后缀是什么示例
能力接口XxxProvidertyping.Protocol，只声明签名MetadataProvider
共享实现基类XxxBase具体类，供同族插件复用逻辑SourceBase（现 SourceProvider）
具体插件XxxPlugin注册进 REGISTRY 的实例WereadPlugin、OPDSPlugin

用 Protocol 而非 ABC：现有 26 个 provider 均不继承任何基类，Protocol 可零改动加上类型检查。

4.2 领域类型

@dataclass(frozen=True)

# 由现有 dict 构造器原地升格

保留原设计最正确的决定：逐项失败内联（failures）必须保住。它让“10 条成功 2 条失败”形成 partial，成功项照常落库、失败项可单独 retry；若改用抛异常表达逐项失败，就只能全盘回退。

4.3.1 TransformProvider 签名与触发配置

class TransformProvider(Protocol):
    supported_formats: frozenset[str]           # {"EPUB", "TXT"}
    supports_auto_trigger: bool = False         # 仅客观可判定的处理（如编码修复）可为 True

    def preview(self, src: ToolInput, ctx) -> ToolReport: ...              # read，不改书
    def apply(self, src: ToolInput, out_dir: str, ctx) -> ToolOutput: ...  # write，改书

# config_schema 中的动态触发选项，用户可随时切换
"config_schema": {
    "type": "object",
    "properties": {
        "trigger": {"type": "string", "enum": ["manual", "auto"], "default": "manual"},
    },
}

supports_auto_trigger=False 的插件，其 config_schema 不包含 auto 选项，前端也不渲染该开关——避免让用户配出一个平台会拒绝执行的组合。

4.4 ExtraFeatureProvider 与它的约束

通用 execute(action, params) 不是错的设计，错的是它当了唯一接口。现在它退回第 7 个接口，专门装标准化不了的东西——插件自带的、只有其工作台界面懂的功能。

class ExtraFeatureProvider(Protocol):
    def execute(self, action: str, params: dict, ctx: PluginContext) -> dict: ...

# manifest 声明白名单，平台按 schema 校验参数
"extra_features": {
    "statistics":         {"mode": "read", "schema": {...}},
    "popular_highlights": {"mode": "read", "schema": {...}},
    "underline_stats":    {"mode": "read", "schema": {...}},
}

# 单条通用路由取代所有插件专属查询路由
POST /api/plugins/{plugin_key}/features/{action}
必须设的约束，否则逃生舱会变成绕过类型系统的万能后门：
  1. 返回裸 dict 只允许出现在这一个接口，其余六个必须返回领域类型。
  2. 能映射到标准接口的必须映射。评审判据：如果一个 action 返回的东西本质上是书、笔记、评分、书源条目之一，它就不该在 extra_features 里。
按此判据，微信读书 11 个 operation 中只有 3 个够格留在 extra。

4.5 capabilities 成为承重声明

CAPABILITY_INTERFACES = {
    "metadata.lookup":     MetadataProvider,
    "annotations.import":  AnnotationProvider,
    "reviews.import":      ReviewProvider,
    "book_sources.search": SourceProvider,
    "book_sources.browse": SourceProvider,
    "integrations.tool":   TransformProvider,      # 三个文本工具同属一个能力：都是对 book content 做处理
    "push.device":         PushProvider,
}

def register(self, plugin):
    manifest = PluginManifest.validate(plugin.manifest)
    if not callable(getattr(plugin, "execute", None)) and not _implements_any(plugin):
        raise TypeError("%r 未实现任何能力接口" % type(plugin).__name__)
    for cap in manifest.raw["capabilities"]:
        iface = CAPABILITY_INTERFACES.get(cap)
        if iface and not isinstance(plugin, iface):
            raise TypeError("%s 声明了 %s 但未实现 %s" % (plugin, cap, iface.__name__))

声明了却没实现 → 进程启动即失败；实现了却没声明 → 平台不会调用它。capabilities 从装饰字段变为承重字段，同时解决 F-5 与 F-8。

capability 不做过度切分：原有 integrations.content_edit / content_convert / encoding_fix 三个能力串合并为一个 integrations.tool。三者都是对书籍正文做处理，形状相同、权限相同、UI 分组相同，切成三份只增加维护成本而不携带任何平台可用的信息。

5. 书源接口（按 Legado 与微信读书实测签名校准）

书源是能力面最宽的一类。接口按功能最完整的 Legado 校准，再回套 OPDS，反向做一定会漏。

5.1 实测链路

# Legado：identity 是 URL，且 toc_url 与 book_url 是两个不同的 URL
detail   = engine.book_info(book_url)      # → BookDetail（内含 toc_url）
chapters = engine.toc(detail.toc_url)      # ← 必须用 toc_url
body     = engine.content(ch.url, clean)   # ← chapter_url

# 微信读书：两层嵌套分页，三种不同的分页键
notebooks = loop(/user/notebooks, lastSort)       # 外层
for book in notebooks:
    marks   = /book/bookmarklist(bookId)
    reviews = loop(/review/list/mine, synckey)    # 内层

5.2 接口

DownloadMode = Literal["single_book", "by_chapters", "none"]

class SourceProvider(Protocol):
    download_mode: DownloadMode      # 由 manifest 声明，register 期按模式校验方法

    # 找书
    def search(self, query: str, cursor: Cursor, ctx) -> Page[SourceBook]: ...           # read
    def browse(self, category_id: str, cursor: Cursor, ctx) -> Page[SourceBook]: ...     # read
    def get_categories(self, ctx) -> list[Category]: ...                                 # read
    # 详情（必需）
    def get_book(self, external_id: str, ctx) -> SourceBookDetail: ...                   # read
    # download_mode == "single_book"
    def download(self, book: SourceBookDetail, ctx) -> BookFile: ...                     # read（只取回字节，入库由平台负责）
    # download_mode == "by_chapters"
    def get_toc(self, book: SourceBookDetail, ctx) -> list[SourceChapter]: ...           # read
    def get_chapter(self, chapter: SourceChapter, ctx) -> SourceContent: ...             # read
    # 运维
    def self_check(self, ctx) -> CheckReport: ...                                        # read
三处按实测修正：
  • get_toc 收 SourceBookDetail 而非 external_id——否则插件内部要为拿 toc_url 再发一次 book_info 请求。平台在 download_book 中本就先调 get_book()，detail 顺传零成本。
  • get_chapter 收 SourceChapter 而非 chapter_id——Legado 的 content() 吃的是 ch.url。
  • Category.id 与 external_id 必须是完全不透明的字符串。Legado 用 URL 作 identity，平台不得解析、拼接或当整数使用。

5.3 取书由平台按模式编排

REQUIRED_BY_MODE = {
    "single_book": ("download",),
    "by_chapters": ("get_toc", "get_chapter"),
    "none":        (),
}

def download_book(plugin, external_id, ctx):
    book = plugin.get_book(external_id, ctx)            # 两种模式都先拿详情
    if plugin.download_mode == "single_book":
        return import_file(plugin.download(book, ctx))
    if plugin.download_mode == "by_chapters":
        return assemble_from_chapters(plugin, book, plugin.get_toc(book, ctx), ctx)
    raise PluginRuntimeError("book_source.download_unsupported", "该书源不支持下载入库")

assemble_from_chapters 由现有 SaveOnlineBookService._do_save() 提为通用编排，承担 N 次 get_chapter 的限流、进度、断点、部分失败与组装入库；插件一行都不写。get_toc / get_chapter 是 read 模式无副作用，在线阅读直接复用它们，不经过 download_book。

6. 运行时与调用模式

6.1 read / write / sync 三种模式

判据是插件行为的副作用方向，不是平台拿到结果后做什么。平台把读来的数据落库，那是平台的编排，与插件方法的模式无关。

维度readwritesync
方向外部 → 平台平台内部（改书）平台 → 外部
插件做什么取数并返回，无副作用修改本地书籍正文把本地数据写进外部服务
典型方法search_books / list_annotations / download / get_chapterTransformProvider.applypush_annotation / PushProvider.push
所需 scope*.readbooks.write*.sync
必须审计 run否（批量摄入的 run 由平台编排产生）是是
幂等要求无按备份恢复必须，避免重复推送
回滚不适用文件备份恢复可能不可用，外部服务未必支持删除
此处修正了先前的错误定义。早先把模式判据定为“是否修改 Talebook 的数据”，据此把 list_annotations 与 download 划为 write。这是错的：插件只是从远端读，写库的是平台。 按修正后的判据，download 只负责取回字节，取回之后如何入库是上层业务逻辑的事，与插件无关，因此是 read； 真正的 write 只有修改书籍正文这一类，目前仅 TransformProvider.apply。
模式决定权限与安全约束，不决定平台编排。 平台调 list_annotations（read）后把结果落库，仍然会创建 PluginRun 与来源记录、推进游标——那是平台摄入流程的职责，不因方法是 read 而取消。 模式回答的是三个问题：需要哪种 scope、是否必须留审计、失败后能否回滚。
顺带收口的安全问题：三种模式与 permissions 已有的 books.read / books.write 词汇同轴，运行时可在派发前强制校验 scope。当前 context["scopes"] 只是传给插件、指望其自觉，执行期从不检查。

6.1.1 sync 模式：外部回写

协议此前只能单向摄入。新增 sync 后，插件可以把 Talebook 的数据写回外部服务，典型场景是把用户在 Talebook 里做的划线笔记回写到 BRS。

class AnnotationProvider(Protocol):
    def list_annotations(self, ctx) -> Page[Annotation]: ...                       # read
    def push_annotation(self, item: Annotation, state: SourceState, ctx) -> PushReceipt: ...  # sync

@dataclass(frozen=True)
class PushReceipt:
    source_annotation_id: str = ""
    source_position: str = ""
    source_raw_hash: str = ""
    source_updated_at: str = ""
这不是从零设计：webserver/services/annotation_sync.py 已经实现了完整的扇出机制—— register_writer(source_name, writer, source_connection_id) 注册钩子、 AnnotationSource 表记录每个来源的 pending / synced / failed 状态与错误、 exclude_source_name 防止回写给数据来源本身造成回环。 但生产代码中没有任何一处调用 register_writer，只有测试注册过（tests/test_annotations.py:310-311）——因为协议里没有 sync 接口，插件无从注册。

本方案把这套机制接入协议：平台在连接启用时，自动为每个实现了 push_annotation 的插件连接注册 writer，register_writer 从公开 API 降为内部实现细节。现有 writer 签名 writer(annotation_dict, source_dict) -> dict 正是 push_annotation 的弱类型版本，返回的四个字段直接对应 PushReceipt。

sync 特有的风险：外部写入通常不可回滚。rollback 对 sync 只能做到“标记来源记录为已撤销并尝试调用插件的删除接口”，插件不支持删除时必须把该项记为 conflict 而非静默成功。回环防护必须保留：从某来源导入的笔记不得再回写给该来源。

6.2 运行时入口与实体落库

class PluginRuntime:
    def read(self, connection, method, *args):
        """解密凭据 + 超时 + 退避重试 + health 更新；不动游标、不写来源记录"""
    def write(self, connection, method, input_data=None):
        """完整 run 状态机 + 游标 + 来源记录 + 回滚"""

# 落库改为按类型派发，if entity_type == "annotation" 与 weread import 一并消失
WRITERS = {Annotation: AnnotationWriter(), Review: ReviewWriter(), SourceBook: SourceBookWriter()}
writer = WRITERS[type(item)]

weread_annotations.py 拆为通用 AnnotationWriter（来源记录、偏移定位、去重、回滚）加微信读书特有的身份策略对象（source_name、external id 前缀、identifiers 匹配字段）。source_name 改为从 connection / plugin_key 推导，不再是模块常量。

消掉：12 个 elif 分支、33 行 weread 硬编码、handler 内的凭据解密。

得到：每次查询自动更新 connection.health；失败进审计，不再出现「管理页显示健康、实际一直 401」。

并发约束（必须遵守）：元数据查询必须并发发起。现有 plugin_search_books 与 plugin_search_books_stream 已用 ThreadPoolExecutor 并发跑 tasks，改造后保持并发不变。 但现有 task 是纯 API 调用、不碰数据库，而 runtime.read 会更新 connection.health——多个工作线程共用一个 SQLAlchemy session 不是线程安全的。 因此运行时提供 read_many(connections, method, *args, timeout=…)：
  1. 在调用线程内预先解密全部连接的凭据，构造只读的 PluginContext；
  2. 线程池内只做网络 I/O，worker 不得触碰 session；
  3. join 后回到调用线程统一写 health、last_tested_at 与审计。
流式接口同理：worker 只回结果，session 写入发生在事件循环所在线程。
兼容性：plugins/meta/ 下 13 个 legacy 源需要逐个包一层适配到 MetadataProvider。它们本就各有 KEY 常量与 search() 方法，适配层很薄；迁移期两条路径可并存，connections_for 返回空时回退到旧分支。

11. 决策记录

编号决策理由被否方案
D-1用 Protocol 而非 ABC 定义能力接口现有 26 个 provider 均不继承任何基类，Protocol 可零改动加类型检查ABC：需逐个改继承，改动面无谓扩大
D-2三种模式 read / write / sync，判据为插件行为的副作用方向read 是外部→平台、write 是改本地书籍正文、sync 是平台→外部，三者方向互斥且各自需要不同的权限与回滚语义两模式且判据为“是否修改 Talebook 数据”——该判据把 download 与 list_annotations 错划为 write，实际写库的是平台不是插件
D-3书源用单一胖接口 + 可选方法避免协议名组合爆炸；“声明不支持”比“未实现某 Protocol”更直白拆 FileAcquireProvider / ChapterReadProvider 三协议
D-4取书方式用 download_mode 枚举声明一个枚举替掉两个 capability 串加一张映射表；前端可直接据此决定 UI用 capabilities 做方法粒度探测
D-5get_toc / get_chapter / download 收领域对象而非 idLegado 的 toc_url 只能从 book_info() 取得；收 id 会导致每次下载多一次 HTTP 请求统一收 external_id（形式整齐但有实际性能代价）
D-6保留通用 execute(action, params) 作为 ExtraFeatureProvider通用 execute 不是错的设计，错的是它当了唯一接口；标准化不了的功能需要有合法去处强行把阅读统计、社区划线塞进标准接口
D-7纳入：plugins/sending/ 更名为 plugins/push/，6 个设备推送器包装为 talebook.push.* 插件用户决定。形态本就是插件：需每用户配置（设备地址）、发网络请求、会失败、需留痕；此前由 handler 用一张 dict 直接实例化，无连接、无 health、无审计不纳入（形态明显契合，无理由排除）
D-8文本工具纳入插件体系而非移出F-4 的审计缺口必须补，而补审计最自然的锚点就是 PluginRun；走 TransformProvider 是顺手一起解决移出插件目录做成“书库工具”（改动更小，但审计仍需另建机制）
D-9异常类改名为 Upstream*Provider 已被指定为能力接口后缀，ProviderAuthError 会被误读为接口错误保留 Provider*（原判断，因命名约定确定而改变）
D-11正文处理提供 trigger 动态配置（manual 默认 / auto 自动处理新书），仅 supports_auto_trigger=True 的插件可选 auto自动改写用户刚上传的文件不可逆；编码错误是客观事实可自动判定，查找替换与繁简转换依赖用户意图全局默认开启；三个工具都提供自动触发
D-13提供 runtime.read_many()：凭据预解密、worker 不碰 session、join 后统一写 health元数据查询必须并发，但 SQLAlchemy session 非线程安全；把 DB 访问约束在调用线程是唯一不引入 session 池的解法每个 worker 各建 session（连接数放大、事务边界难控）；串行查询（首屏明显变慢）
D-12integrations 下三个 capability 合并为一个 integrations.tool三者都是对书籍正文做处理，形状、权限、UI 分组完全相同，切分不携带任何平台可用信息保留 content_edit / content_convert / encoding_fix 三串（“capability 描述意图”的说法不足以支撑维护成本）
D-10先用 Legado 验证书源接口，再回套 OPDSLegado 能力面最宽（含分章读取、分类发现、规则体检）；先按 OPDS 定义必然漏项先做 8 个 OPDS 族（快但会固化错误抽象）
