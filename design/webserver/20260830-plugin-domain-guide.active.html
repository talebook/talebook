重建插件领域模型与开发指南

以当前运行时代码和已经确认的产品边界为事实源，统一插件、能力、Provider、启用状态和连接所有权等概念，重写一份稳定、可执行的开发指南。

状态：ACTIVE 创建日期：2026-08-30 所属模块：webserver 影响范围：CONTEXT.md、document/PluginGuide.md 需求来源：用户要求使用 domain-modeling 重整插件设计体系

1. 原始诉求

“使用 domain-modeling 重新整理 plugin 的设计体系，重写 PluginGuide.md。”

现有指南混合了分支交接、历史 PR 决策、产品入口和运行时契约，并且仍介绍已经删除的 auto_install、ensure_auto_installations() 和不可运行的 MetadataProvider 示例。它无法继续作为插件开发的权威入口。

2. 目标与边界

目标

  • 建立无实现细节的插件领域词汇表。
  • 让开发指南准确覆盖身份、目录、Manifest、能力、生命周期、所有权、运行时与 API。
  • 提供一份符合当前类型契约的最小可运行插件示例。
  • 明确划线笔记、本地权威数据与 BRS 外部副本的关系。

非目标

  • 不改变运行时代码、数据库或现有 API。
  • 不设计第三方插件下载、上传和进程隔离机制。
  • 不把所有内部 HTTP 接口包装成公共稳定 API。
  • 不为历史 PR 和临时分支维护交接说明。

4. 领域模型

核心结论：插件是产品与生命周期单元，能力是业务发现边界，Provider 是实现角色，连接是配置与凭据的所有权边界，运行是审计边界。
插件定义声明稳定身份、版本、能力、权限与配置契约。
插件启用状态管理员决定当前实例是否开放该内置插件。
实例或用户连接由相应所有者保存公开配置、加密凭据和授权范围。
能力调用与运行业务按能力发现连接；运行时统一审计、超时、重试和健康状态。

需要避免的等同关系

  • 插件不等于 Provider；一个综合插件可以由一个 Provider 实现多种能力。
  • 启用不等于已配置，也不等于健康。
  • combo 不等于 Manifest 的 integrations 分类。
  • 用户连接不等于租户配置；当前所有权主体是具体 Talebook 用户。
  • 额外功能不等于通用执行入口；能标准化的行为必须走类型化能力。

5. 开发指南结构

  1. 指南定位与权威事实源。
  2. 领域模型和状态判定。
  3. 插件 ID、代码目录与唯一注册入口。
  4. Manifest v1 字段、配置 Schema、安全与 UI 声明。
  5. 七类类型化 Provider 契约和额外功能逃生舱。
  6. 运行时调用模式、连接发现、超时重试、审计与分页。
  7. 全局配置和个人设置的产品边界。
  8. 各能力的专项约束，包括元数据、书源、划线笔记、书籍工具和发送到设备。
  9. 管理 API、个人 API 与业务 API 的职责边界。
  10. 最小可运行插件、注册步骤、测试与提交检查。

历史分支进度、一次性迁移表和某个 PR 的选择不再进入长期开发指南；必要时由对应 ACTIVE 方案保存。

6. 影响、风险与回滚

影响范围

新增根级领域词汇表，整体替换插件开发指南，并新增本次内部方案。没有运行时、数据库、接口或页面行为变化。

保持不变

现有插件 ID、Manifest v1、注册清单、默认启用状态、管理入口、个人连接和业务 API 全部保持不变。

主要风险：文档把当前实现细节误写成长期保证。缓解方式是明确“协议契约”和“当前平台实现”的层级，并用源码与契约测试逐项校验示例。

回滚：本次只修改 Markdown 和内部 HTML，按文件回退即可，不涉及数据清理。

界面审查：本次没有页面、交互、文案资源或前端消费者变化，不需要执行 interface-review；剩余风险仅为文档准确性。
