管理员设置保存保留内部配置

修复系统配置页面只保存页面白名单字段、导致 MariaDB 连接串、已激活主题等内部配置从 auto.py 消失的问题，同时保持接口写入白名单，并让失败保存不提前污染运行态或留下半写文件。

状态：ACTIVE 创建日期：2026-08-06 所属模块：webserver 影响范围：AdminSettings、SettingsLoader、配置落盘 需求来源：Multica TAL-5 / GitHub Issue #944

原始诉求与复现

管理员保存任意系统配置后，现有 MariaDB user_database 会在重启或重新加载时恢复为默认 SQLite；ACTIVE_THEME 等不由该页面编辑的配置也会丢失。接口目前新建 SettingsLoader 后立即 clear()，再仅写入请求中的白名单字段，因此生成的 auto.py 只剩本次页面提交内容。

基线复现：只提交 site_title 后，生成文件仅包含 installed 与 site_title，不再包含 user_database 或 ACTIVE_THEME。

目标与边界

  • 以当前服务端完整配置为保存候选，只覆盖明确列入页面白名单或合法 SOCIAL_AUTH_* 模式的请求字段。
  • 保存后 MariaDB 连接、激活主题及其它非页面配置在运行态和重新加载后保持不变。
  • 未知字段、非完整匹配的动态键和 Python 语法型恶意键继续被忽略，不能借“保留配置”扩大客户端可写范围。
  • auto.py 使用同目录临时文件、刷新并 fsync 后通过 os.replace 原子替换；异常时清理临时文件并保留原文件。
  • 所有持久化步骤成功后才更新 CONF；失败响应不能留下候选运行态。

非目标：不重构设置页面、不改变数据库迁移流程、不新增可编辑配置项，也不把所有任意 CONF 键开放给请求。

保留与授权分离

“保留已有键”是服务端基线行为；“允许客户端修改键”仍由现有 KEYS 与锚定的 SOCIAL_AUTH_SETTING_RE 决定。请求中的 user_database、ACTIVE_THEME 或构造动态键不会进入覆盖循环，但服务端已经持有的同名配置会原样留在候选中。

失败一致性

SettingsSaverLogic 不再在写盘前调用 CONF.update()。Nuxt 环境文件按候选配置生成并保留旧快照；随后原子写入 auto.py。若第二步失败，使用旧快照恢复 Nuxt 环境文件；无论哪一步失败，均不提交运行态。单个配置文件的替换使用同目录临时文件，避免跨文件系统替换和进程中断导致截断。
