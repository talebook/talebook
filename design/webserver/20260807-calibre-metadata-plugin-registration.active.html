slim runtime 的 Calibre 元数据插件注册修复

让 production slim 镜像中的 Google 与 Amazon.com 元数据源进入 Calibre identify 注册表，并用真实调度链路测试防止“插件缺失却静默返回空结果”。

状态：ACTIVE 创建日期：2026-08-07 所属模块：webserver 影响范围：Calibre 初始化、元数据查询、Docker 测试 需求来源：Multica TAL-7 / GitHub Issue #907

原始诉求与根因

production 镜像使用 talebook/talebook-base:slim-v8.5.0。镜像保留了 google.py 与 amazon.py，但设置了 standalone converter 模式并裁掉 calibre.devices。完整的 calibre.customize.builtins 因设备模块缺失而无法导入，standalone 内置集合又不包含元数据源，最终 identify 注册表为空。

已在固定 digest sha256:4bca0299…be5e 中复现：initialize_plugins() 后 identify 插件为 []；现有 patch_plugins() 只替换已经注册的插件，不能创建缺失项。

目标与边界

  • 启动 Calibre 后，Google 与 Amazon.com 都能在启用的 identify 注册表中找到。
  • 只在来源缺失时补充 slim 镜像内已有的官方插件类；完整 Calibre runtime 保持原初始化结果。
  • 初始化必须幂等且并发安全，不能重复注册或在请求并发时重建注册表。
  • 请求的来源仍不可用时，抛出带来源名称的专用异常并写错误日志，不能伪装成普通空结果。
  • 测试必须经过真实 calibre.ebooks.metadata.sources.identify.identify() 调度；只替换已注册插件实例的网络方法以提供可控结果。

非目标：不恢复 slim 镜像中全部设备驱动，不修改 talebook-base，不改变元数据源优先级、搜索结果格式或外部站点协议。

方案

注册策略

新增一个带锁的幂等初始化函数。它先读取 metadata_plugins({"identify"})；只有目标来源缺失时，才从镜像中现存的 Calibre source 模块导入类，加入 standalone 的 builtin_plugins 与 builtin_names，并调用 Calibre 自身的 initialize_plugins() 完成实例化、排序和配置应用。

调用与诊断

init_calibre() 在 Calibre 路径建立后主动执行初始化，避免首次并发请求重建注册表。查询入口仍重复做廉价幂等检查以覆盖直接调用。目标插件缺失时使用 CalibreMetadataSourceUnavailable，且 ISBN/书名包装层不吞掉该异常。

剩余风险：该修复使用 Calibre UI 模块暴露的 registry globals 补齐 standalone 集合，Calibre 大版本改变内部接口时可能需要同步调整；已通过固定 8.5.0 production 测试与明确失败诊断控制。本次在 amd64 production 镜像验证，未执行 arm64/armv7 容器；逻辑不含架构分支。外部 Google/Amazon 网络可用性不属于注册修复的稳定测试条件，因此测试用可控插件动作隔离网络。
