演示模式：自动开户与伪管理员面板

在已上线的单账号只读演示模式基础上，去掉“部署者需手工预建 demo 账号”的门槛，并让 demo 账号能够体验管理员设置面板——但看到的是出厂默认参数、点击保存也不会真正改变任何运行配置。

状态：ACTIVE 创建日期：2026-08-01 所属模块：webserver 影响范围：登录鉴权、用户数据模型、管理员设置接口、演示模式策略 需求来源：PR #887 评论 @hehetoshang（2026-08-01）

原始诉求

PR #887（Issue #886 的实现）评论区中，@hehetoshang 提出：

“我希望打开演示模式时自动创建一个名为 demo 的用户，然后密码是 demodemo，然后 demo 用户可以查看管理员面板，但是内部内容为虚假体验版，可以进入演示管理员面板，内部的内容为 settings.py 设置的默认参数，并且点击保存按钮是不会真的去保存的。”

拆解为三个可验证的行为点：① 演示模式生效时不再要求部署者预先创建账号；② 配置的 demo 账号能进入“管理员设置”页面；③ 该页面显示的是 webserver/settings.py 里的出厂默认值而非真实运行配置，且提交保存请求返回成功但不写入任何配置。

与既有方案的关系

本方案建立在已生效的 design/webserver/20260721-single-account-demo-mode.active.html（单账号只读演示模式）之上，复用其“单账号判定 / 只读写保护”基础设施，但直接推翻了该方案里的两条“非目标”：

20260721 方案的非目标（现状）

  • 不自动创建、重置或定期清理演示账号。
  • 不修改现有角色和权限位，也不把演示账号强制改为管理员。
→

本方案的目标（新增）

  • 演示模式下，demo 账号首次登录即自动开户，密码固定为 demodemo。
  • demo 账号不获得数据库里的真实 admin 权限位；“能看到管理员面板”是仅针对设置页面的伪造视图，不解锁其余管理接口。

其余部分（写请求统一拒绝、WebDAV 只读、不记录访问痕迹等）不变，本方案不重复描述，只覆盖新增的开户与伪管理员面板行为。旧方案已随本方案生效改为状态 SUPERSEDED（design/webserver/20260721-single-account-demo-mode.superseded.html），并在其中注明由本方案取代上述两条非目标，原因见上表；旧方案其余设计仍然有效，由本方案继续复用，不再重复维护。

目标与非目标

目标

  • 演示模式开启后，任何人以配置的 DEMO_USERNAME、密码 demodemo 登录时，若账号不存在则自动创建（非管理员、可登录、无自定义权限位）。
  • 已存在同名账号时不覆盖、不重置密码，自动开户逻辑幂等。
  • demo 账号可以看到“管理员设置”页面，但读取到的是 settings.py 里的默认参数，不泄露真实部署的密钥、数据库地址、当前站点标题等运行配置。
  • demo 账号提交“保存设置”会收到成功响应（模拟真实保存的交互反馈），但后端不写入 CONF、不落盘 auto.py。
  • 用户信息接口对 demo 账号展示 is_admin: true，使前端既有的管理员入口自然可见，不需要新增前端代码。

非目标

  • 不把 demo 账号的数据库 admin 字段设为真，因此其余 @is_admin 管理接口（用户管理、书籍批量删除、书源管理等）仍然拒绝 demo 账号，返回既有的权限错误。
  • 不为管理员设置页面之外的其它页面单独构造“虚假数据”，管理员面板的其它子页面在本方案后仍不可用，留作后续按需扩展。
  • 不在管理后台提供“开启/关闭演示模式”的开关，仍只能通过配置文件控制。
  • 不改变 20260721 方案里关于只读写保护、WebDAV、社交登录禁用等既有行为。

方案

1. 自动开户：登录时按需创建，而非启动时创建

新增 webserver/demo_mode.ensure_demo_account(conf, session)：仅在演示模式开启且配置了 DEMO_USERNAME 时生效；先按用户名查询，存在则直接返回，不存在才创建一条 admin=False、active=True、无自定义权限位（权限位留空即按既有 has_permission 语义默认放行）的账号，密码固定为常量 DEMO_DEFAULT_PASSWORD = "demodemo"（走既有 bcrypt 哈希，不明文存储）。

调用点选在 SignIn.post()：当按用户名查不到账号、且演示模式开启、且用户名等于配置的 DEMO_USERNAME 时才触发开户，随后复用既有密码校验、can_login() 等流程，不改变原有登录判定顺序。选择“登录时按需创建”而非“服务启动时创建”，是因为后者依赖 main.py 里数据库表已就绪的时序，且在测试、多进程部署等场景下不易保证只执行一次；登录时创建复用了同一条查询-写入路径，天然幂等，也不需要改动启动流程。

2. 伪管理员视图：只在“设置页”内特判，不动真实权限位

AdminSettings 新增 is_demo_fake_admin()：演示模式开启且当前登录账号是配置的 demo 账号时为真。GET 在该条件下返回 webserver/settings.py 里的原始 settings 字典（出厂默认值）而不是合并了 auto.py/manual.py 覆盖的运行时 CONF，避免把真实部署的站点标题、AI Key、数据库连接串等展示给公开演示访客。POST 在该条件下只做 JSON 解码（保证接口不报 500），直接返回 {"err": "ok", "rsp": data}，不经过原有的字段白名单过滤、SettingsSaverLogic.save_extra_settings()、写 auto.py 等真实保存路径。

该特判只加在 AdminSettings 一个 handler 里，不修改 BaseHandler.is_admin() 或全局 @is_admin 装饰器，因此其它管理接口对 demo 账号的判定完全不受影响，继续依据数据库里真实的 admin 字段拒绝。

3. 演示模式只读策略的例外：放行“假保存”这一条 POST 路径

demo_mode.request_is_allowed() 新增 DEMO_FAKE_SAVE_PATHS = {"/api/admin/settings"}：仅对该固定路径的 POST 放行，使请求能进入 handler 触发上面的“假保存”分支，而不是在 BaseHandler.prepare() 阶段就被通用只读策略拦成 demo.read_only。放行只发生在路由层面，实际是否允许执行、返回什么内容仍完全由 AdminSettings.post() 内的 is_demo_fake_admin() 判断决定；非 demo 账号即便命中这条路径，也会落回原有 self.admin_user 校验。

4. 前端零改动：复用已有管理员入口与设置页

UserInfo.get_user_info() 对 demo 账号返回 is_admin: true（叠加原有 user.is_admin() 结果，即 user.is_admin() or is_demo_fake_admin）。前端现有的“管理员”导航入口和设置页组件均按此字段显示，无需新增或修改任何 .vue 文件；设置页调用的 GET/POST /api/admin/settings 接口行为已在后端伪造，页面看到的即是默认参数与“保存成功”的提示。

安全边界与风险

  • 不产生真实管理员权限：数据库里 demo 账号的 admin 字段始终为 False，其它所有 @is_admin 保护的接口（用户管理、批量删数据、书源管理、SSL 证书、日志下载等）不受本方案影响，继续拒绝 demo 账号——这是本方案刻意收窄的范围，避免“伪管理员”被误用为真实提权入口。
  • 不泄露真实配置：设置页对 demo 账号只读出 settings.py 里写死的出厂默认值，不合并 auto.py/manual.py 覆盖，真实部署的第三方密钥、数据库连接串、真实站点标题等不会经此接口泄露。
  • 固定密码是已知风险，但已被既有只读策略兜底：demodemo 是公开可预期的密码，任何人都能登录 demo 账号；这本身符合“公开演示账号”的定位，且登录后仍受 20260721 方案里全局的只读写保护约束，不能执行真实的业务写操作。
  • 幂等开户避免竞态覆盖：开户逻辑先查后建，若账号已被部署者手工创建（例如自定义了更强的密码），不会被自动流程覆盖或重置密码。
  • 放行面收窄到单一路径：只读策略的例外只加了 /api/admin/settings 一条，不是放开整个 /api/admin/* 前缀，降低误放行到破坏性接口（如批量删除、迁移数据库）的风险。

决策记录

  1. 2026-08-01：明确“自动开户”的触发时机选在登录请求内按需创建，而不是服务启动阶段，理由是避免依赖启动时序、天然幂等、且不需要改动 main.py 的会话生命周期。
  2. 2026-08-01：明确“伪管理员”的范围仅限管理员设置页面，不把 demo 账号数据库 admin 字段置真，避免放大到其它管理接口造成真实数据风险；用户请求里的“管理员面板”按上下文（“内部内容为 settings.py 默认参数”“点击保存不会真的保存”）理解为设置页面，而非整个后台。
  3. 2026-08-01：只读策略的放行范围收窄到 /api/admin/settings 单一路径，而不是整个 /api/admin/* 前缀，降低误放行破坏性接口的风险。
  4. 2026-08-01：固定密码 demodemo 直接采用需求原文给出的值；开户逻辑先查后建，已存在账号不会被自动流程覆盖密码。
