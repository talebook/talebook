阅读器笔记入口开关：浮动入口的显隐归阅读器设置

登录读者在线阅读时，右上角的「阅读笔记」浮动入口无法关闭。本方案把它的显隐做成阅读器设置里的一项偏好，宿主模板只消费阅读器透出的状态：不加后端接口，不动笔记数据，两个仓库可以独立发布。

状态：ACTIVE 创建日期：2026-09-28 所属模块：webserver 影响范围：图文书阅读器模板与 spec/阅读器.md；配套 candle-reader 阅读器设置 需求来源：用户诉求「把页面上我圈出来的图标开发一个可以自由打开关闭的功能性开关」

1. 原始诉求

“帮我写一个完整的拉取请求，把页面上我圈出来的图标开发一个可以自由打开关闭的功能性开关。”

圈出的对象是登录读者阅读页右上角的浮动入口「阅读笔记」（#annotation-toggle，带笔记条数角标）。它当前固定显示：读者觉得它压住正文时没有别的选择，而它又是进笔记面板的唯一入口，所以「关掉」必须可逆。

已核实的事实：这个入口不在 candle-reader 里，而是 Talebook 自己的 creader.html 渲染的；阅读页的正文、底部导航和设置面板都由 candle-reader 渲染。因此本方案要先回答「开关归谁」，再谈怎么隐藏。

2. 目标与边界

目标

  • 登录读者用一个开关让浮动入口显示或隐藏，重新打开即恢复。
  • 开关归阅读器设置，按浏览器保存，不需要新接口与后端改动。
  • 关掉入口只改变入口的可见性，不改变任何一条笔记数据。
  • 宿主模板不引入第二份偏好来源，两侧可以独立发布。

非目标

  • 不改笔记数据模型与 /api/book/<book_id>/annotations 接口。
  • 不做按书、按设备或服务端同步的偏好。
  • 不改游客行为——游客本来就看不到该入口。
  • 不代替 candle-reader 正在推进的「笔记 UI 收口」；本方案的开关语义是「入口是否出现」，收口完成后仍然成立。

4. 现状、根因与证据

观察权威证据结论
浮动入口固定显示，没有开关webserver/resources/book/creader.html 的 #annotation-toggle（仅登录读者渲染）入口的所有权在宿主模板，不在阅读器
阅读页其余部分由阅读器渲染creader.html 里 new Reader('#app', …) 加载 candle-reader.es.js阅读器已经有设置面板，是开关的现成落点
阅读器设置与宿主同源EpubReader.vue 的 save_settings() 写 localStorage.readerSettings宿主可以在首屏同步读到这份偏好，无需新接口
入口隐藏后不应还能被键盘选中入口是原生 <button>，当前始终在 Tab 序中隐藏方式必须真正移出可达序列，而不是只做视觉遮挡
事实与推断：推断「阅读器设置面板在移动端始终可达」已由底部导航「设置」入口证实；未验证的是读者在真实书库中对默认值的接受度，这属于产品观察，不影响本次实现。

5. 方案

方案结论：开关的所有权放阅读器设置（它本来就管「阅读界面里有什么」），宿主只让出自己那份入口的显隐。阅读器把偏好透出成 <html> 上的一个属性，宿主用一条 CSS 消费它——跨仓契约只有一个属性名加一条选择器，没有新接口。
Input读者切换「笔记入口」

阅读器设置面板里的显示 / 隐藏，默认显示

Guard读写偏好

写入 localStorage.readerSettings.notes_entry，并同步 <html data-candle-reader-notes-entry>

Core宿主消费属性

一条 CSS 让浮动入口 display:none；首屏脚本先读一次 localStorage，避免入口闪现

Output入口显隐

隐藏时同时移出 Tab 序与无障碍树；笔记数据与接口零变化

关键决策

决策点选择理由放弃项
开关的所有权放阅读器设置，宿主只消费状态入口属于阅读界面，阅读器已经在管界面构成；宿主再存一份会出现两套偏好在 Talebook 模板里自建开关与存储（读者换个阅读器就丢掉偏好，且与阅读器设置面板重复）
跨仓契约<html> 上的 data 属性 + 宿主 CSS宿主不需要接回调或事件；运行中切换也能立刻生效；属性是纯 DOM 状态，易断言自定义事件或 postMessage 回调（宿主需额外接线，首屏仍要单独处理）
首屏表现宿主在 <head> 同步读一次 readerSettings阅读器挂载前入口就会渲染，只靠阅读器设置会出现「先出现再消失」只依赖阅读器挂载后设置属性（入口闪现）
关闭的语义只隐藏入口，不碰笔记数据诉求是「图标可以打开关闭」，不是关闭笔记能力关闭时同时停掉笔记加载（会改变数据语义，超出诉求，也和主开关重复）
 
阅读器（candle-reader）
  设置项 notes_entry（默认 true）
    → localStorage.readerSettings.notes_entry = false
    → document.documentElement.dataset.candleReaderNotesEntry = 'off' | 'on'

宿主（talebook creader.html）
  <head> 首屏脚本（避免闪现）：
    var saved = JSON.parse(localStorage.getItem('readerSettings') || '{}')
    if (saved.notes_entry === false) {
      document.documentElement.setAttribute('data-candle-reader-notes-entry', 'off')
    }

  样式（两侧共用的唯一一条规则）：
    html[data-candle-reader-notes-entry="off"] #annotation-toggle { display: none !important; }

6. 影响范围、风险与回滚

影响范围

本仓库：webserver/resources/book/creader.html 新增一条 CSS 与一段首屏脚本，tests/test_annotations.py 新增渲染断言，spec/阅读器.md 新增「5.7 笔记入口」并补第 4、7 节。配套仓库 candle-reader：设置面板新增「笔记入口」，设置默认值新增 notes_entry，并透出到 <html>。

保持不变

笔记表与接口、隐私与可见性规则、游客行为、浮动入口的位置样式与无障碍名称、笔记面板本身、阅读器与宿主的既有初始化参数。

主要风险：阅读器与宿主版本错配（宿主先更新而阅读器还是旧包）→ 触发条件是读者没有新的设置项，因此根本看不到开关，不会出现「关了没反应」；反向（阅读器先更新）→ 旧宿主不认识该属性，入口照常显示，属于功能未生效而非故障。缓解方式是两个仓库都可独立发布，且契约只依赖一个属性名。另一风险是 localStorage 不可用（隐私模式、禁用 Cookie）→ 首屏脚本整体 try/catch，保持入口默认显示。
回滚：两个仓库各自以提交为单位回滚，无需数据迁移；偏好键是阅读器设置里的一个新字段，老版本会忽略它，不产生残留状态。
交付顺序：宿主侧改动只有在新的 candle-reader 静态包上线后才会真正生效，candle-reader-version.txt 需要随发行包一起升级。反过来先升宿主、后升阅读器是安全的：旧阅读器没有该设置项，读者看不到开关，入口行为与现在完全一致。
