统一书源能力命名空间

删除插件协议中重复的 book_ 限定，让目录类型、Plugin ID 与 Capability 共同使用 source 领域词根。

状态：ACTIVE 创建日期：2026-08-30 所属模块：webserver 影响范围：插件协议、内置 Provider、前端消费者、测试与开发指南 需求来源：用户要求删除 book_sources 的 book_ 前缀

1. 原始诉求

“哪些地方使用了 book_sources？应当统一用词规范，去掉 book_ 前缀。”

现状同时存在目录 source/、Plugin ID talebook.source.*、协议类别 book_sources 与能力 book_sources.*。同一个领域概念出现两套英文词根，增加注册、能力发现和前端判断的认知成本。

2. 目标与非目标

目标

  • Manifest category 改为 sources。
  • Capability 改为 sources.search、sources.browse、sources.acquire。
  • 运行时、Provider、消费者、mock、测试与开发指南使用同一协议词汇。
  • 在首次发布前冻结正确的 talebook.plugin/v1 契约，不引入过渡命名。

非目标

  • 不重命名 Plugin ID，继续使用 talebook.source.*。
  • 不重命名 Python SourceProvider。
  • 不迁移数据库表 book_sources。
  • 不修改现有 HTTP 资源路径 /api/book-sources。
  • 不重写历史 ACTIVE / SUPERSEDED 方案中的原始决策文本。

4. 领域与协议决策

统一语言：领域称“书源能力（Source Capability）”；代码目录为 source；Plugin ID 为 talebook.source.*；Manifest category 为 sources；标准能力为 sources.search / browse / acquire。

版本边界

book_sources.* 与 sources.* 不同时存在。插件协议尚未对外发布，本次属于第一版冻结前的命名修正，因此继续使用 talebook.plugin/v1，不提供别名、双写或兼容转换。当前产品只装配随系统交付的内置 Provider，启动时会重新物化 Definition；Installation、Connection、Run 和书源业务表均不以 Capability 作为主键，因此开发数据无需迁移。

兼容边界

  • Plugin ID 和安装记录身份保持不变。
  • 已有 Connection 继续绑定同一 installation。
  • 书源 HTTP API 路径与响应结构保持不变；响应中的 capabilities 使用第一版正式名称。
  • 无需处理发布版本或外部插件兼容性；本地开发数据由内置 Definition 重新物化。

5. 实施范围

  1. 协议常量与 Capability-to-Protocol 映射。
  2. 所有 source Provider Manifest 与 SourceCatalog 能力集合。
  3. 插件管理测试接口、前端能力测试器和前端 mock。
  4. 后端契约、运行时、API 和书源测试中的期望值。
  5. CONTEXT.md 与 document/PluginGuide.md。
  6. 增加守卫：生产代码与当前测试不得再出现协议 token book_sources；只允许数据库表名和明确的兼容说明。

6. 风险与回滚

风险

遗漏一个 Capability 消费者会让已启用书源无法被发现；遗漏前端 mock 会让自动化测试与真实 API 漂移。

缓解

全仓检索精确 token，增加无旧命名守卫，运行 Manifest/Runtime/API/书源定向测试，并检查插件管理与网络书库关键页面。

回滚：本次不迁移表和身份字段；回退协议常量、Manifest 与消费者即可。新产生的 Definition 行仍使用同一 Plugin ID/版本并可在下次启动时被覆盖。
