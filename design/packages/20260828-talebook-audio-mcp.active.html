Talebook Audio CLI MCP 接入

让 OpenXiaoAI Bridge 像调用 neteasecli 一样，通过常驻 stdio MCP 子进程浏览和播放 Talebook 有声书，同时复用已验证的 Bridge StreamPlayer 后端。

状态：ACTIVE创建日期：2026-08-28所属模块：packages影响范围：CLI 协议、Bridge 配置与部署需求来源：HOU-20

1. 原始诉求

“能不能与bridge接入个mcp，就是与网易cli与bridge接入mcp的方式一样”

现有 CLI 已能通过 --player xiaoai 调用 Bridge StreamPlayer，但 AI 对话还不能发现书目、选择章节或控制播放。本次把这些能力暴露成 MCP 工具，并接入用户指定的 /opt/open-xiaoai-bridge 实例。

2. 目标与边界

目标非目标
提供 talebook-audio mcp stdio server；列书、列章节、按书或版本播放；暂停、恢复、停止、上一章、下一章和状态；播放结果返回 Bridge 静默结束信号；真实部署和工具调用可复现。不通过 MCP 接收或保存密码；不修改 Talebook 服务端；不新增 HTTP MCP 监听；不把 Cookie、Bridge token 或请求头暴露给模型；不改变 neteasecli 工具。

3. 现状与证据

  • /opt/open-xiaoai-bridge/config.py 已用 stdio 方式常驻启动 neteasecli mcp，并由 MCPClientManager 聚合工具。
  • Bridge 识别 structuredContent["x-open-xiaoai-bridge"] 的 end_turn_silently / playback_started 信号；播放工具必须复用该契约。
  • Talebook CLI 已具备安全登录会话、书目与章节解析，以及 OpenXiaoAI StreamPlayer 的播放和控制能力。
  • MCP 官方 Python SDK 在 Bridge 的 /app/.venv 中可用；宿主机未安装，因此 SDK 作为可选依赖并保持普通 CLI 无额外依赖。

4. 方案

方案结论：在 CLI 包内新增异步 MCP 控制器与官方 SDK stdio 入口。控制器持有当前 Talebook 章节队列和 Bridge 播放器；所有阻塞 HTTP 调用通过工作线程执行，后台监控在章节结束时自动续播。部署只挂载 CLI 源码和受权限保护的会话目录，Bridge token 使用既有只读路径。

5. 影响范围、风险与回滚

  • 代码：新增 MCP server/controller、CLI 子命令、可选 SDK 依赖、测试和文档；普通命令保持兼容。
  • 部署：新增只读 CLI 源码挂载、读写会话目录挂载和一个 MCP server 配置；Bridge 容器需重建一次。
  • 凭据：管理员先在宿主机登录一次；MCP 不接收密码。会话目录和 Cookie 保持 0600，Bridge token 不进入工具参数或结果。
  • 风险：完整章节下载会让播放工具调用持续约 14 秒；timeout 设为 180 秒。后台自动续播和显式切章可能竞态，使用单一异步锁与监控任务串行化。
  • 回滚：从 mcp_servers 删除 talebook_audio 并移除两项挂载后重建单个容器；CLI 代码回滚为独立提交，不涉及数据迁移。

7. 决策记录

  1. 2026-08-28：用户明确要求复用 neteasecli → Bridge 的 MCP 方式；选择 stdio 而非新增网络监听。
  2. 2026-08-28：不提供登录 MCP 工具，避免模型上下文和工具参数承载密码；采用管理员预登录的 0600 会话目录。
  3. 2026-08-28：使用官方 SDK 作为可选依赖；Bridge 部署复用其现有 SDK，普通 CLI 仍保持零运行时依赖。
