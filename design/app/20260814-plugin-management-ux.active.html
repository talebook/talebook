插件管理与既有能力迁移

以「管理 → 插件」统一四类业务入口；现有非 AI 元数据、Generic OPDS 与 Legado 继续使用原配置和数据表，同时获得统一目录、连接健康与执行记录。

状态：ACTIVE日期：2026-08-14模块：app / webserver需求：TB-43依据：TB-41 定稿
诉求边界架构页面迁移界面审查验证风险

1. 原始诉求

在插件公共底座与 UX 定稿后，实现 /admin/plugins 的元数据、笔记（含章评）、评价、书源四个 Tab；提供目录、详情、搜索/筛选、启停、连接测试、执行记录、失败项重试与回滚入口；把 Talebook 既有非 AI 元数据、Generic OPDS 和 Legado 能力迁入，保留旧入口一版兼容跳转，并确保数据库只有一套事实。

验收重点是升级后旧配置、启用状态和核心行为零回退，既有能力进入统一插件目录并共享底座运行治理。实现输入来自 TB-41 批准的交互稿 20260814-plugin-management-ux.wip.html。

2. 范围与硬边界

本次交付

  • 四 Tab 目录、状态优先卡片、搜索与状态筛选，筛选写入 URL。
  • 右侧详情弹窗、权限、连接健康/测试、最近运行和安装启停。
  • 全局执行记录、单次运行明细、失败项重试与可回滚运行入口。
  • 复用现有 OPDS 导入弹窗和 Legado 管理页；旧书源路由兼容跳转。
  • 内置能力注册、旧状态迁移、API 和回归测试。

明确排除

  • 不接入 AI，也不把 AI 元数据源写入插件目录或状态摘要。
  • 不接入 Calibre Content Server 或 Calibre-Web。
  • 不复制 OPDS、Legado 或元数据配置，不改变其既有业务数据表。
  • 不在本次引入任意代码热加载、插件市场或新的 Secret 展示方式。

3. 实现架构

1. 注册定义三个 trusted builtin provider 声明 category、capability、权限与管理动作。
2. 幂等迁移首次访问目录时创建共享 installation 与无凭据 instance connection。
3. 读取旧事实元数据设置、OpdsSource、BookSourceModel 实时形成配置/启用摘要。
4. 统一治理测试、健康和后续执行进入 plugin runs；旧业务仍走成熟 adapter。

5. 迁移与兼容决策

  • 单一事实：OPDS 仍读写 OpdsSource，Legado 仍读写 BookSourceModel，元数据仍读取现有 settings；插件表只保存统一 definition、installation、connection 与 run 治理数据。
  • 幂等启动：每个内置能力只创建一条共享安装和一条“内置连接”；重复访问不会重复迁移。
  • 启用状态：元数据 installation 首次取现有 auto_fill_meta；各来源配置/启用数量实时从旧事实计算，停用插件不删除旧配置或已导入数据。
  • 行为复用：元数据配置跳回原设置锚点；OPDS 与 Legado 直接复用现有组件和 API，避免并行实现导致功能回退。
  • 安全：普通序列化不暴露 Secret；本次三个内置 provider 的 auth schema 为空，因此不制造虚假凭据，也不放宽需认证 provider 的校验。

8. 风险与后续

兼容风险

  • 旧入口承诺保留一版；未来删除前需确认外部书签与文档已迁移。
  • 插件安装启停是治理开关，不反写或删除每个旧来源的单独启用状态。
  • 完整 HTTP API 回归依赖 Calibre 运行环境，本机只能完成纯 SQLAlchemy 与浏览器 mock 验证。

演进方向

  • 新增真实第三方 provider 时复用现有四 Tab 和 connection/run API，不增加第五个日志 Tab。
  • 写入型 provider 应提供独立 preview/review 工作区，再进入执行与来源治理。
  • 把成熟旧业务逐步接入 source records 时，仍保持旧域表为事实源并用 adapter 事务桥接。
