恢复历史结果，不替用户重新搜索

网络书库仍可即时展示本地缓存的上次关键词与结果，但只有用户明确提交搜索或切换结果页时才发起搜索请求。

1. 原始诉求

“每次打开在线书库，它都自动开始上一次的搜索，我都没搜，它就自己搜”

外部用户报告每次进入网络书库都会重跑上一次搜索。正文只作为现象描述；本方案依据仓库代码与自动化验证确定修复。

2. 目标与边界

目标

  • 重新进入 /network 时不自动发起 /network/search。
  • 保留上次关键词、模式、选择源和缓存结果的即时恢复。
  • 用户点击搜索、回车或翻页时仍正常请求最新结果。

非目标

  • 不删除或迁移现有 localStorage 缓存。
  • 不改变后端搜索接口、轮询任务和缓存容量。
  • 不改动搜索页视觉布局、文案或书源加载。

3. 现状与证据

位置现状判断
app/pages/network/index.vueonMounted 恢复 store.last 后调用 fetchSearch(searchPage.value)。页面进入动作直接触发真实搜索，与用户报告一致。
git blame自动刷新与本地缓存恢复在同一历史改动中引入。不是后端任务残留，而是明确的前端挂载行为。
app/test/e2e/network.spec.ts已有用例验证缓存结果恢复，但未统计再次进入时的搜索请求。需要增加负向请求断言防止回归。

4. 方案

进入页面读取本地缓存，恢复关键词、搜索范围、页码与已有结果。
加载书源只请求 /network/sources，不因缓存存在而启动搜索。
显式操作用户提交搜索或点击分页后，才调用既有 fetchSearch。

实现约束

删除挂载阶段的 stale-while-revalidate 分支，保留缓存读取与 searched 状态恢复。E2E 在完成一次搜索、离开并重新进入后统计 search API 请求数，断言计数不增加，同时继续断言关键词和结果可见。

5. 影响与风险

缓存可能不是最新结果。这是取消隐式网络操作的直接取舍；用户可点击搜索显式刷新。页面仍会加载最新书源列表，后端协议和数据兼容性不变。

7. Grill 决策记录

设计问题结论理由
是否完全清除上次搜索？否，继续恢复缓存。问题指向“自动开始搜索”，缓存展示本身不产生网络任务，且已有明确回退体验与测试。
是否保留后台 revalidate？否。任何自动 revalidate 都会重新启动上次搜索，无法满足诉求。
是否增加刷新按钮或新文案？否。现有搜索按钮已经提供显式刷新能力，增加界面不解决根因。
是否修改后端任务取消机制？否。根因发生在新页面挂载后的主动请求，不是旧任务继续运行。
