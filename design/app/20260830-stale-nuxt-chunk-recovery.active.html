失效 Nuxt chunk 自恢复

让旧 Readest Worker 即使先返回了不含新清理脚本的旧 HTML，也能通过已经失效的 Nuxt JavaScript URL 进入恢复流程。

状态：ACTIVE创建日期：2026-08-30所属模块：app影响范围：Nuxt dev middleware、Nitro error handler、SPA/SSR Nginx需求来源：PR #977 第三次白屏反馈

1. 原始诉求

“仍然如此：旧 entry.Qt6l3l2G.css 返回 application/json，CKHYTMRW.js 404。”

上一方案的全局清理脚本只存在于新 HTML。旧 Worker 的 offline-cache 使用 3 秒 NetworkFirst：Nuxt 首次编译或 SSR 超过 3 秒时，它先返回旧 HTML；旧 HTML 不含清理脚本，因此形成恢复死锁。

2. 目标与边界

  • 未知 /_nuxt/*.js 不再返回 JSON/HTML 404，而返回一个很小的 JavaScript 恢复模块。
  • 恢复模块注销旧 Readest Worker、删除确定属于它的缓存，并使用仅一次的查询参数重新导航。
  • 已存在的 hash 资源继续按原路径和缓存策略提供，不拦截正常 chunk。
  • 只处理 JavaScript 失效资源，不把 404 全局改成 200。

3. 方案

命中旧引用旧 HTML 请求已删除的 Nuxt JS hash。
脚本兜底Vite dev middleware、Nitro 404 handler 或 Nginx try_files 返回恢复模块。
清理污染复用精确 Worker 识别与 Readest 缓存清理。
强制取新页带一次性查询标记导航；即使无 Worker，也绕过旧 HTTP HTML。

生产 Nginx 对稳定恢复模块设置 no-store、nosniff；Nitro 仅将 /_nuxt/*.js 的 404 改写为恢复模块，真实静态资源仍优先返回。

4. 风险与回滚

  • 恢复循环：查询标记和页面级全局锁保证同一 URL 最多自动恢复一次。
  • 掩盖真实部署缺包：第二次仍缺资源时不再刷新，保留控制台错误供排障。
  • 误拦截正常资源：测试实际构建 chunk 内容与 MIME，确认静态资源优先于恢复 handler。
  • 残留缓存：旧 Worker 可在最后一次导航时重建 offline-cache；新页面根据恢复标记再清一次。
  • 回滚：删除 dev middleware、Nitro error handler、Nginx JS fallback 与恢复模块，不涉及数据迁移。
