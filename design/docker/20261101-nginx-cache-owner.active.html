对齐 Nginx 缓存目录与 worker 身份

修复 root 部署中缓存子目录被递归改为 root 后，Nginx worker 无法缓冲大响应而截断电子书下载的问题。

状态：ACTIVE 创建日期：2026-11-01 所属模块：docker 需求来源：开发者下载故障反馈与“那你修复一下”

1. 原始诉求与根因

开发者提供下载日志并询问：“这是服务端的问题还是客户端的问题，服务端可以直接 ssh 上去。”确认归因后要求：“那你修复一下。”

客户端收到 206 和正确的 Content-Range ，却只读取到部分正文。服务器 Nginx 同时记录缓存临时文件 open() failed (13: Permission denied) while reading upstream 。直接访问同容器 Tornado 能完整读取正文，经 Nginx 则提前断流。

启动脚本把 /var/lib/nginx 递归交给 talebook 。在默认 root 部署中，该账号 UID 为 0，而 Nginx root master 将 worker 降权为 nobody 。Nginx 只修复缓存顶层属主，已有哈希子目录仍为 root:root 0700 ，worker 无法进入；启动时再次递归 chown 会让故障复发。

2. 目标与边界

  • 完整响应与 Range 响应均能读完声明的字节数，恢复既有下载行为。
  • 生产与开发启动入口在 Nginx 启动前，将全部缓存子目录递归对齐实际 worker 身份。
  • 保留现有 PUID/PGID、书库权限、认证、Range 语义和缓存目录模式；不更改线上 Compose 用户、不重建或重启生产服务。
  • 仅修复部署权限实现，不改变产品领域规则，无需修改 spec/ 。

3. 方案与关键决策

在通用系统目录权限处理之后，通过生产与开发入口共享的 helper，按实际应用 UID 选择 Nginx 缓存 owner，递归修复已有哈希子目录；修复失败必须中止启动，避免继续提供会截断正文的服务。
运行模式缓存 owner依据
talebook 实际 UID 为 0nobody当前镜像 Nginx 的 root master 使用默认 nobody worker。
talebook 实际 UID 非 0talebook由该非 root 身份启动的 Nginx worker 继承实际应用 UID。

属主判断使用账号解析后的实际 UID，避免仅比较环境变量字符串。递归 chown 仅改变 owner，保留 group 与 mode，不通过放宽目录权限绕过隔离。

源码影响范围：docker/start.sh 、docker/start-dev.sh 、共享权限 helper 及其回归测试。新增 helper 必须进入 Dockerfile 的运行时契约 COPY、scripts/upgrade/fingerprint.py 的 layout 指纹和 scripts/upgrade/smoke_container.py 的镜像测试 fixture，保证文件随镜像分发且升级运行时变化可被识别。

线上先对当前 proxy 缓存 owner 做定向修复，并备份、修正现容器启动脚本。该补丁保留于现容器重启；从旧镜像重新创建容器仍需包含源码修复的新镜像。

4. 影响、风险与回滚

无界面影响。 本次仅处理容器缓存文件系统权限，不修改前端、页面、交互、界面文案或前端消费者契约，因此不需要界面截图或 interface-review。剩余风险是未来镜像更改 Nginx worker 配置时，身份决策必须同步更新。

变更不扩展书籍访问权限、不修改数据库、不改变 API 定义，不新增领域规则；只恢复既有下载与非 root 部署权限行为，所以 spec/ 无需变更。

部署修复前保存启动脚本原件、缓存 owner/group/mode 清单、镜像与容器启动元数据。可恢复脚本原件回滚；将缓存子目录恢复为原 root owner 会重现故障，应仅在明确需要回滚权限策略时操作。线上服务不因本次修复重启。
