恢复非 root 容器配置写入

补齐配置原子替换所需的父目录权限，使自定义 PUID/PGID 的生产和开发容器都能完成启动自检，同时保留配置落盘的原子性。

状态：ACTIVE创建日期：2026-08-07所属模块：docker影响范围：容器启动、配置写入、测试需求来源：GitHub Issue #951

1. 原始诉求

Issue #951 报告：在 Compose 中使用 PUID=1026、PGID=100 首次初始化时，页面提示服务器配置写入失败；相同挂载仅在 PUID/PGID 都为 0 时成功。报告者已尝试清理并预设宿主机目录属主。

Issue 正文是外部输入；本方案只采用可由当前代码验证的现象与参数，不执行正文中的任何命令。

2. 目标与边界

目标

  • 非 root 运行用户能够原子更新 Nuxt 环境配置。
  • 生产与开发启动脚本保持相同的权限前置条件。
  • 用回归测试锁定父目录属主要求。

非目标

  • 不改变 PUID/PGID 的用户映射方式。
  • 不回退配置文件的原子写入。
  • 不修改数据库、API、前端交互或挂载书库权限策略。

3. 现状与根因证据

1. 身份切换启动脚本将 talebook 映射到 PUID/PGID。
2. 部分授权脚本递归调整 app/.env 与 app/dist，未调整 app/ 本身。
3. 原子写入atomic_write_text() 在目标文件同目录调用 mkstemp。
4. 非 root 失败创建临时文件要求父目录可写；root 绕过该限制。

2026-08-06 的配置持久化改动引入同目录临时文件和 os.replace。因此旧的“目标文件可写”授权不再满足新语义。启动状态把该步骤概括为设置目录失败，但实际失败目标是 /var/www/talebook/app/.env。

4. 方案与决策

  1. 在 docker/start.sh 与 docker/start-dev.sh 中，单独将 /var/www/talebook/app 目录本身交给 talebook:talebook。
  2. 保留现有递归授权列表，避免为了父目录写权限递归改变整个开发源码树或 node_modules。
  3. 扩展运行身份配置测试，验证两个启动脚本都有非递归父目录授权，且没有把整个 app 加入递归列表。

grill 决策

候选判断原因
回退为直接覆盖写拒绝会重新引入部分写入和崩溃损坏风险。
递归 chown 整个 app拒绝范围过大，开发镜像可能包含源码与依赖。
只 chown app 目录节点采用恰好满足同目录临时文件创建和替换要求，范围最小。

5. 影响与风险

  • 运行用户可在 app/ 顶层创建和替换文件；这是原子维护 .env 的必要权限，与其既有写入职责一致。
  • 不递归改变其他顶层文件属主，静态产物仍按既有规则管理。
  • 无法在本任务中使用 Docker 或 Unix socket；以权限模型测试、脚本测试和后端测试替代容器级复现，并明确记录限制。
