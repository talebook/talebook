Talebook 前端镜像构建去重

创建日期：2026-07-21 所属模块：docker 状态：ACTIVE 需求来源：GitHub Issue #888「优化构建速度」
将单个、串行生成 SPA 与 SSR 的前端构建阶段拆成共享依赖层和两个独立构建分支：SPA 目标只生成 SPA，SSR 目标并行生成 SSR 与其兼容所需的 SPA 静态目录，同时保持已有 Docker target 与镜像内容语义。

原始诉求与现状

维护者要求执行 Issue #888“优化构建速度”。当前目标提交中的 Dockerfile 只有一个 builder 阶段：先运行 npm run build 生成 SSR，再运行 npm run build-spa 生成 SPA。任何引用该阶段的目标都必须完成两次构建。CI 分别请求 production-spa 和 production-ssr，且使用独立缓存作用域，因此每个平台的冷路径共执行四次 Nuxt 构建。

GitHub Issue 页面因当前公共网络连接重置无法补取正文；本方案只处理仓库内能够直接证明的重复工作，不推断或修改其他构建策略。

grill 决策与边界

问题决策理由
优化哪条链路Docker 前端生产构建图重复的 SPA/SSR 命令在 Dockerfile 中可直接复现和静态验证。
是否修改 CI否任务明确禁止修改 .github/workflows/；现有 target 调用保持兼容。
是否改变产物否SSR 镜像继续包含既有 dist/ 兼容目录；启动脚本和后端静态路径仍引用该目录。默认 logo、配置与运行时符号链接也保持不变。
如何验证收益构建图回归测试任务禁止访问 Docker socket，无法在本次 workflow 内安全执行真实镜像构建或计时。

方案

frontend-deps 只复制 lockfile 并执行 npm ci。builder-spa 与 builder-ssr 分别复制源码并只生成自身产物。后端和数据预构建逻辑放入不含前端产物的 production-common；SPA 与 SSR 目标从该公共阶段分叉，再复制对应产物和默认 logo。

production 继续表示 SPA，production-spa 继续作为其别名。production-ssr 从 SSR 分支复制 .output，并从 SPA 分支只复制既有的 dist/ 兼容目录；两个独立分支可由 BuildKit 并行执行。Makefile 与 workflow 的 target 名称无需改变。理论冷路径由每个平台四次 Nuxt 构建降至三次，并消除 SSR 目标内两次构建的串行依赖；实际耗时收益由合并后的 Actions 运行确认。
