TALEBOOK · CONTAINER IDENTITY NOTE

让 UID 0 只有一个名字

创建日期：2026-07-22 所属模块：docker 状态：ACTIVE 需求来源：GitHub Issue #761

保留 PUID=0 / PGID=0 的兼容能力，但不再把 talebook 账户强行改成与 root 重复的数值身份。运行时按 UID 与 GID 分别复用已有 root 身份或映射 talebook 身份。

原始诉求与结论

维护者要求检查“容器内使用 PUID=0 导致的刮削错误”是否存在，并在确认后给出完整 PR。当前生产和开发启动脚本都会执行 usermod -o -u "${PUID}" talebook 与 groupmod -o -g "${PGID}" talebook。当值为 0 时，系统同时存在 root 与 talebook 两个同 UID/GID 条目；Calibre 及其子进程按数值反查账户时，身份名称和主目录不再唯一。

结论：问题存在。修复重点不是增加刮削重试，而是消除启动阶段制造的重复系统身份。

实现范围

文件计划变更
docker/setup-user.sh集中解析 PUID/PGID；0 复用 root，非 0 映射 talebook；导出统一运行身份并更新 nginx worker 身份。
docker/start.sh / docker/start-dev.sh复用身份脚本，权限修复使用已解析的运行身份。
conf/supervisor/*.confgosu 从固定 talebook:talebook 改为读取启动脚本导出的身份。
webserver/self_check.py自检、数据库同步和迁移使用相同身份，避免启动阶段与 Tornado 身份不一致。
tests/覆盖四种 0/非 0 组合、非法输入、Supervisor 配置与 self-check 运行身份。

非目标

  • 不修改元数据抓取逻辑、数据源协议、数据库结构或前端交互。
  • 不对既有书库执行额外迁移；权限标记变化时仍由启动自检按当前身份修复 /data/books。
  • 不移除 PUID/PGID 兼容配置，也不要求使用 root 的 NAS 用户改部署文件。

风险、兼容与回滚

  • 兼容：非 0 的常见配置保持原行为；0 仍获得对应 root 用户或组权限，只是不再创建重复账户记录。
  • 一致性：nginx、启动自检、Tornado 与 SSR/dev Node 进程使用同一解析结果。
  • 安全：使用 0 仍意味着以 root 权限运行，这是用户显式配置；默认镜像继续使用 1000，不扩大默认权限。
  • 回滚：恢复启动脚本内的直接 usermod/groupmod 和 Supervisor 固定用户即可；无数据格式变化。
