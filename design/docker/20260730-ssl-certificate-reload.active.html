Request & scope

修复功能，不绕开功能

原始诉求

继续处理 Issue #761 的运行身份问题；不能因为权限实现复杂就废弃 SSL 上传。需要确认 slim runtime 下的真实行为，并给出比整套身份重构更直接、可完整验证的方案。

目标

  • 默认 PUID=1000、PGID=1000 时，管理员上传合法证书后立即完成 Nginx 热加载。
  • Nginx master、worker 与 Tornado 均以动态映射后的 talebook 身份运行；只有 Supervisor 与一次性 bootstrap 保留 root。
  • Nginx 继续监听容器内 80/443，Docker 对外端口和现有证书路径保持不变。
  • 配置检查或热加载失败时恢复旧证书，不能出现“接口报错但新证书留在磁盘、重启后意外生效”。
  • 实现同时覆盖静态生产镜像与 SSR 生产镜像，并通过真实 Docker 与 Chrome 操作验收。

非目标

  • 不移除 SSL 上传，不要求用户改用 Caddy、Traefik 或宿主机反向代理。
  • 不改变 /data/books/ssl/ssl.crt 与 /data/books/ssl/ssl.key。
  • 本次不禁止 PUID=0；它保留为显式兼容配置，但不再是 SSL 上传的必要条件。
  • 不处理 Calibre Google/Amazon 元数据插件未注册问题；该问题由 Issue #907 独立跟踪。
Observed on master

当前故障发生在 reload 权限，不在 Chromium

默认身份稳定失败Chrome 上传请求进入 Tornado 后，nginx -t 因无法访问 root 所有的 /run/nginx.pid 返回权限错误。
写盘先于检查接口虽然返回失败，新证书却已覆盖存量文件；当前 Nginx 仍使用旧证书，下一次容器重启会加载“失败”的新证书。
PUID=0 能成功所有进程均变为 root 后，检查与 reload 成功，证明证书功能本身可用，但该方式扩大了整个应用的权限。
已确认结论

slim 基础镜像不包含 Qt/Chromium，已消除旧版 Calibre 触发 Chromium root sandbox 的路径；但这不会修复 Nginx PID 文件与信号权限。两类问题必须分开处理。

当前调用顺序

SSLHandlerLogic.run() 先写正式证书，再执行 nginx -t 和 service nginx reload。Handler 既承担 HTTP 行为，也承担文件事务与进程控制，失败恢复没有形成明确接口。

实现约束

  • 镜像构建时只给 /usr/sbin/nginx 添加 cap_net_bind_service=+ep，不把能力授予 Python、Node 或整个容器。
  • docker/start.sh 在动态修改 talebook UID/GID 后创建并授权 /run/talebook、/data/books/ssl、Nginx 日志与临时目录。
  • Nginx 主配置中的 PID 路径改为 /run/talebook/nginx.pid；证书路径与站点配置保持不变。
  • Supervisor 的静态生产与 SSR 配置都使用 user=talebook 启动 Nginx；dev 配置同步，避免开发与生产身份模型分叉。
  • 启动自检以 talebook 身份运行 nginx -t，验证真实运行权限，不接受 root 检查造成的假阳性。

Certificate state

一次上传只有“完整生效”或“恢复旧值”

新增内部深模块 SSLCertificateManager，对 Handler 只暴露一个安装接口。临时文件、备份、权限、Nginx 检查、热加载与失败恢复都留在模块实现内部；HTTP Handler 不再知道操作顺序。

01 · validate

校验上传

在 SSL 目录创建临时文件，校验证书链与私钥匹配；失败不触碰正式文件。

02 · prepare

锁定与备份

获取更新锁，保存旧证书和私钥，候选文件落盘并设置确定权限。

03 · install

原子替换

用同目录 os.replace 分别替换正式文件，避免单个文件出现半写状态。

04 · verify

检查配置

以 talebook 运行 nginx -t；错误时立即恢复旧文件。

05 · activate

热加载

执行 nginx -s reload；成功后删除备份并返回 err: ok。

统一回滚规则：配置检查或 reload 任一步失败，使用同目录临时文件与 os.replace 恢复旧证书，再检查旧配置；reload 已被请求但失败时，再尝试恢复旧配置的 reload。若恢复本身失败，返回独立的 rollback 错误并完整记录服务端日志，不能伪装成普通 reload 失败。

文件契约

  • 正式路径仍为 /data/books/ssl/ssl.crt 与 /data/books/ssl/ssl.key。
  • 证书权限固定为 0644，私钥固定为 0600，属主为动态映射后的 talebook。
  • 临时文件与备份必须位于同一目录，确保 os.replace 不跨文件系统。
  • 成功、失败与异常退出都清理临时文件；锁只保护一次安装事务，不暴露给 Handler。
  • reload 使用 nginx -s reload，不再依赖 Debian init 脚本 service nginx reload。
Compatibility & risk

外部接口保持，内部权限收窄

保持不变

  • 管理员 SSL 上传接口及前端交互。
  • 容器内 80/443 与 Docker 端口映射。
  • 正式证书、私钥和数据卷路径。
  • PUID/PGID 的动态 UID/GID 映射。
  • 静态诊断页和 bootstrap 启动自检。

明确变化

  • Nginx master 从 root 改为 talebook。
  • PID 文件移入 talebook 可管理的运行目录。
  • Nginx 二进制获得唯一的低端口绑定能力。
  • 上传失败不再保留候选证书。
  • PUID=0 仍可用，但不再作为 SSL workaround。
  • 能力保留构建后使用 getcap /usr/sbin/nginx 验证文件能力；实际以 PUID 1000 监听 80/443，防止多阶段 COPY 或打包过程丢失扩展属性。
  • 启动顺序SSL、日志、PID 与 Nginx 临时目录必须在 Supervisor 启动前完成授权，否则非 root Nginx 无法提供诊断页。
  • SSR 一致性SSR 镜像继承 production 后覆盖 Supervisor 配置，必须同步 Nginx 用户配置；Node 运行身份不变化。
  • 显式 rootPUID=0 会把名为 talebook 的账户映射到 UID 0。本次为兼容保留，并在容器日志中输出安全提示；是否禁止需另立方案。

发布与回滚

不涉及库表、数据迁移或证书路径迁移。镜像回滚到旧版本后仍能读取同一组正式证书。若新镜像无法启动，可直接回滚镜像标签；数据卷不需要执行逆向转换。

验收结论与已知告警

  • 默认 PUID 1000、SSR 与显式 PUID 0 三类运行方式均到达 ready，证书热更新不再要求整套应用以 root 运行。
  • Chrome 实际验证了管理员设置页的匹配证书成功路径与错误配对路径；成功请求后的在线证书与磁盘证书指纹一致。
  • 本机 Nuxt 常规文件监听触发 EMFILE，改用 Chokidar polling 后完成验收；这只影响本地测试启动方式，不影响镜像运行。
  • 浏览器仍显示既有 Vuetify i18n 缺失 key 告警；Nginx 仍提示既有 listen ... http2 弃用告警。二者均不影响本次 SSL 流程，且本次不扩大范围处理。
