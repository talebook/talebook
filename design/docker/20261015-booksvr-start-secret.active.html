修复 booksvr 启动密钥传递

修复 production 镜像启动时 cookie_secret 未传入 booksvr 的问题，并让自检只在后端实际启动后报告就绪。

状态：ACTIVE创建日期：2026-10-15所属模块：docker需求来源：用户要求修复启动错误

1. 原始诉求

“给我改好”

容器启动日志显示 booksvr 因缺少 BOOKSVR_COOKIE_SECRET 重试并进入 FATAL；Nginx 仍返回静态页面，但 API 返回 502。

2. 目标与边界

  • booksvr 由 Supervisor 启动时能读取同一 Talebook 配置中的 cookie_secret。
  • 自检仅在 supervisorctl 成功启动 booksvr 后写入 ready。
  • 不触碰现有书库内容或密钥值；容器替换时保持现有端口与挂载。
  • 一并消除启动脚本对不存在的 /root/.config/calibre 执行 chown 的报错。

3. 现状、根因与证据

self_check 将密钥放在 supervisorctl 子进程环境中，但 supervisorctl 向已运行的 supervisord 发 RPC；目标进程使用 supervisord 管理器的环境，不继承 supervisorctl 的环境。启动日志重复报告缺少密钥，supervisor 状态为 FATAL，/api/book 返回 502。

4. 方案

新增 booksvr 启动包装器，作为 Supervisor 管理进程执行。包装器使用现有安全读取逻辑从 auto.py 加载 cookie_secret，设置 BOOKSVR_COOKIE_SECRET 后通过 exec 替换为 booksvr。自检只请求 supervisorctl 启动，不再试图透传环境变量；启动失败时将状态标记为 failed。将 Supervisor startsecs 调整为 3 秒，避免进程一启动就退出仍被误判为成功。

SPA 与 SSR 两套 production 配置均使用包装器。docker/start.sh 在 chown 前创建 Calibre 配置目录。

5. 影响范围、风险与回滚

影响 Dockerfile、Supervisor production 配置、启动自检和容器入口脚本。无 spec 更新：这是部署启动可靠性修复，不改变书籍领域规则或业务接口。风险是密钥读取仍依赖持久化 auto.py；读取失败时服务保持 failed，不会暴露密钥。回滚可恢复上一镜像标签并重建容器，保留相同 /data 挂载。
