升级运行时目录兼容宽松 umask

v26.10.10 起，升级执行器在启动前检查 /run/talebook-release 的权限。以 umask 0002 启动容器的 NAS Docker 引擎会让这个目录组可写，检查失败导致容器无限重启。本方案让执行器自己保证安全权限，同时保留对可疑目录的拒绝。

状态：ACTIVE 创建日期：2026-10-17 所属模块：docker 影响范围：scripts/upgrade/executor.py；不涉及 spec/ 需求来源：Issue #1086

1. 原始诉求

“v26.10.10版本在飞牛docker下无限重启。v26.09.23版正常。……File "/opt/talebook-upgrade/executor.py", line 101, in prepare: raise UpgradeError("storage")”

来源：talebook/talebook#1086。v26.09.23 尚无应用内升级执行器，所以不受影响。

2. 目标与边界

目标

  • umask 0002 下容器正常启动，内置应用可用，升级功能不被误判禁用。
  • 从 v26.10.10 崩溃循环升级上来、遗留了组可写空目录的容器也能恢复。
  • 不变量：运行时目录为符号链接、非 root 所有，或组可写且内有任何条目时仍拒绝启动。

非目标

  • 不改变 /data/updates 不安全时降级为禁用升级的既有行为。
  • 不调整 start.sh 中 prepare || exit 1 的失败语义。
  • 不处理宿主 umask 对 /data 下书库文件的影响。

3. 现状、根因与证据

观察权威证据结论
容器启动即退出并被重启docker/start.sh 中 executor.py prepare || exit 1prepare 抛错会直接终止容器。
prepare 抛 storagescripts/upgrade/executor.py 原第 100–101 行：RUN.mkdir() 后检查 st_mode & 0o022mkdir 未指定 mode，权限取决于进程 umask；umask 0002 得到 0775，检查失败。
本地复现在 umask 0002 下调用 prepare() 的新增用例，修复前失败报错与 Issue 日志同一行、同一错误码。
事实与推断：飞牛 Docker 以 umask 0002 启动容器是根据报错推断的，未在真机确认；但无论引擎为何给出宽松 umask，修复后的行为都不依赖它。

4. 方案

方案结论：执行器不再信任外部 umask：入口统一设为 0022，运行时目录以 0755 创建；仅当已有目录由 root 所有、组/其他可写且为空时收紧为 0755，其余可疑状态仍抛 storage。

关键决策

决策点选择理由放弃项
新建目录与文件的权限main() 入口 os.umask(0o022)，RUN.mkdir(mode=0o755)release、备份与控制 socket 也由执行器创建；PGID=0 时应用账号属于 root 组，组可写会让应用改写可信代码。只改 RUN.mkdir：其他目录仍会继承宽松权限。
已存在的组可写目录空目录收紧为 0755；非空仍拒绝v26.10.10 的崩溃循环只会留下空目录；非空意味着有人在可写窗口写入过条目，如预置符号链接可让 root 的 atomic_json 覆盖任意文件。无条件 chmod（Codex 评审指出的风险）；清空目录后继续（会删除可能有意义的现场）。
失败语义保持抛 storage 让容器退出运行时目录不可信时无法安全生成 current 指针。降级为禁用升级：仍需写入该目录。

5. 影响范围、风险与回滚

影响范围

仅 scripts/upgrade/executor.py 与其测试。产品行为、API、数据结构均不变，spec/ 无对应篇目需要更新。纯后端改动，无界面影响，因此不需要 interface-review。

保持不变

/data/updates 的安全判定与禁用升级降级；符号链接与非 root 所有者的拒绝；控制 socket 的 0660 权限。

主要风险：若引擎在 umask 之外还以其他方式放宽 /run（如挂载可写卷），非空目录仍会让容器退出，表现与修复前相同；由新增的“非空仍拒绝”用例覆盖该边界。
回滚：回退本次提交即可，无数据迁移；运行时目录每次启动都会重新生成。
