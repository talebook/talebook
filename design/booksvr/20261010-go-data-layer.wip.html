在 Go 里建完整数据访问层：为搬 handler 铺路

把 Calibre LibraryDatabase 的实测调用面（23 个方法）在 Go 里完整实现，作为阶段 6 逐条搬迁 215 条 handler 的基础设施。本阶段不修改任何 Python 代码——Python 注定要删，不给它做数据层优化。

状态：WIP 创建日期：2026-10-10 所属模块：booksvr 影响范围：booksvr/internal/library/、tests/ 需求来源：用户原话「为什么还要python？」

1. 原始诉求

“我的目标从来都是替换 calibre，整个 talebook 的后端换成 go 的 booksvr 呀”
“我要你全改完，怎么还有215个反向代理给tornado呢？”
“为什么还要python？”

阶段 2 完成后，booksvr 已接管 8000 端口成为唯一对外后端，但 215 条路由仍反向代理回 Tornado。

本阶段最初被设计为「数据库层接管」——让 Python 换个方式读库。但用户一句「为什么还要python？」点破了前提错误：Python 注定要删，给它做数据层优化是浪费。

修正后的定位：在 Go 里把数据访问层建完整（读+写），作为搬 handler 的基础设施，不碰 Python。

2. 目标与边界

目标

  • Go 侧实现 Calibre LibraryDatabase 实测调用面的全部能力（读 17 + 写 4）。
  • 搜索语法复刻 Calibre 查询语法（字段限定、比较符、布尔、括号）。
  • 回收站改为 Go 直接读 .caltrash 目录。
  • 字段元信息、封面、格式路径等辅助能力齐备。
  • 与 Calibre 语义一致性的契约测试。

非目标

  • 不修改任何 Python 代码（本次路线修正的核心）。
  • 不实现 handler（属阶段 6）。
  • 不实现元数据文件解析（属阶段 4）。
  • 不实现元数据源插件（属阶段 5）。
  • 不删除 Calibre 运行时（属阶段 7）。

4. 现状、根因与证据

观察权威证据结论
self.db 调用面 23 个方法实测：get_data_as_dict(12)、get_metadata(11)、field_metadata(8)、get_books_for_category(6)、add_format(5)…读 17 + 写 4

5. 方案

在 booksvr/internal/library 包内新增数据访问能力，纯 Go 包，不引入 HTTP——阶段 6 的 handler 是 Go 代码，直接调包即可。

现状：  Python handler ──► self.db (Calibre) ──► SQLite
阶段 3：Go library 包 ──► SQLite（读+写，完整能力）   ← 本阶段只做这个
阶段 6：Go handler ──► Go library 包                  ← 逐条搬，搬完删 Python

5.1 搜索语法（分三步）

  • Step A（已完成）：实测被调用的语法——publisher:/author:/tag:/search:/空查询/全文搜索。
  • Step B（已完成）：补齐 series:/rating:/format:/title:、比较符（:=/:</:>）、布尔（and/or/not）、括号分组。
  • Step C（已知缺口）：正则（~）、虚拟书库、custom_columns 高级查询未实现，遇到时返回明确错误而非静默错误结果。

实现方式：词法分析 → 递归下降解析 → SQL 生成。

5.2 回收站

直读 <library>/.caltrash/b/<book_id>/：列出时扫描目录 + 读 books 表补元数据；恢复时文件移回 <library>/<book.path>/；删除时移除目录。复刻 Calibre 的 commonpath 路径穿越防护。

5.3 写接口

全部在事务内完成：ImportBook 建 books 行 + 关联作者/出版社/标签/简介；DeleteBook 显式清理 9 张关联表（Calibre 无外键级联）；AddFormat 同时写 book_formats 与 Calibre 的 data 表；SetTags 替换标签关联。

6. 影响范围、风险与回滚

风险影响缓解
搜索语法复刻不完整阶段 6 搬 handler 时行为不一致分步实现 + 契约测试；Step C 缺口如实记录
本机无 Calibre 无法真双跑一致性未真实验证用真实 fixture + Python 独立复算；真实双跑记录为未执行项
写接口绕过 Calibre 导致数据不一致书库损坏本阶段不接生产路径，只做单元测试
数据层能力不足阶段 6 才发现缺接口按实测调用面逐项覆盖

回滚

本阶段不接生产路径（纯新增 Go 包），无需回滚——删掉新增文件即可。

未执行项与风险（如实记录）：
  • 真实 Calibre 双跑未执行。本机无 Calibre（ModuleNotFoundError: No module named 'calibre'），无法启动 Calibre 做逐条对比。替代方案：用真实 fixture（tests/cases/metadata.db，13 本书/15 作者/72 标签）+ Python 独立复算期望值。剩余风险：Calibre 的边界行为（如特殊字符、NULL 处理）未逐条比对。
  • 搜索语法 Step C 未实现。正则（~）、虚拟书库、custom_columns 高级查询未实现；遇到时返回明确错误。实测这 3 类语法在仓库中无调用点，风险可控。
