让 booksvr 接管 8000：Talebook 后端流量切换

新增 booksvr serve 子命令，让 Go 后端成为唯一对外 HTTP 入口：已实现的 3 条路由本地服务，其余 215 条显式反向代理回 Tornado（退到 8001），并以灰度开关与回滚路径保证可逐步接管。

状态：WIP 创建日期：2026-10-10 所属模块：booksvr 影响范围：booksvr/、conf/supervisor/、conf/nginx/、webserver/self_check.py、docker/start.sh、tests/ 需求来源：用户原话「整个 talebook 的后端换成 go 的 booksvr」

1. 原始诉求

“我的目标从来都是替换 calibre，整个 talebook 的后端换成 go 的 booksvr 呀”
“岂有此理，没有被调用，booksvr 还有什么用。目标就是替换 calibre，只是部分功能没实现而已”

第一阶段已完成 Calibre 存储层的 Go 重写（作品/版本/格式三层模型、8 步归一化流水线、单向只读迁移），并真实接管了格式路径解析层（format_keys.py 被 get_books() 与 WebDAV 调用，读 book_formats 表）。

但 booksvr 目前没有生产入口：218 条路由已声明，其中仅 3 条有 Go handler，其余 215 条在 NewServer 中因 Handler == nil 被跳过；Dockerfile 只把二进制拷进镜像，没有任何进程启动它。生产流量仍全部由 Tornado 服务。

本阶段要解决的不是「实现全部 215 条 handler」，而是让 booksvr 先站到生产路径上——否则后续每写一个 handler 都没有真实流量验证它。这是绞杀者模式的第一步。

2. 目标与边界

目标

  • booksvr serve 子命令存在，监听 8000，提供 HTTP 服务。
  • 已实现的 3 条路由（/api/work/{id}、/api/book/{id}/versions、/api/book/{id}/merge）由 booksvr 真实提供。
  • 其余 215 条路由显式反向代理回 Tornado（退到 8001），不得静默 404。
  • 灰度开关可按路由控制「走 booksvr / 走 Tornado」，默认全部走 Tornado。
  • 关闭开关后流量完全回到 Tornado，行为与切换前一致（可回滚）。
  • 身份由 booksvr 自行解析 Tornado secure cookie 得到。

非目标

  • 不实现其余 215 条 handler（阶段 3-6 的工作）。
  • 不改变对外 HTTP API 契约：218 条路由的路径、方法、响应结构不变。
  • 不改变 Tornado 的业务逻辑，它只是从 8000 退到 8001。
  • 不删除 Calibre 依赖（阶段 7 的工作）。
  • 不做与流量切换无关的重构。

5. 方案

采用绞杀者模式：booksvr 监听 8000 作唯一对外后端，未实现路由反向代理回 Tornado（8001）。

                    ┌─────────────────────────────────────┐
   Nginx  ────────► │  booksvr :8000  （唯一对外后端）      │
   (反代 8000)       │                                     │
                    │  1. 解析 Tornado secure cookie       │
                    │     → Identity{UserID,IsAdmin}       │
                    │  2. 查灰度开关                       │
                    │     ├─ 命中 booksvr 清单 → 本地 handler│
                    │     └─ 未命中 → 反向代理 ────────┐    │
                    └──────────────────────────────────┼────┘
                                                       │
                                                       ▼
                                        ┌──────────────────────────┐
                                        │  Tornado :8001（兜底）    │
                                        │  215 条未实现路由         │
                                        └──────────────────────────┘

5.1 灰度开关与路由匹配语义

-serve-routes 默认空（全部走 Tornado 兜底），逗号分隔 pattern 或 all。分发器只遍历「有 Go handler 的路由表」（当前 3 条），不遍历 218 条全表——因为全表含 catch-all /(.*)，会造成顺序陷阱。命中但无 handler 仍走代理。

5.2 身份解析

Go 复刻 Tornado secure cookie v2：2|<len(kv)>:<kv>|<len(ts)>:<ts>|<len(name)>:<name>|<len(b64)>:<b64>|<hex_hmac_sha256>。解析顺序对齐 base.py:288-310：lt（7 天）→ user_id → admin_id。只信任自己解析的 cookie，忽略外部身份 header。

已知权限偏差：Python 的 admin_id 会查库取 Reader 并校验 admin 字段；阶段 2 不查库，admin_id 存在即视为管理员。若该用户已被删除或降权，存在权限提升风险。缓解：cookie 有 HMAC 保护、阶段 2 仅 merge 一条路由需管理员权限；阶段 3 改为查库校验。

5.3 密钥下发链路

cookie_secret 不是环境变量，而是安装时写入 /data/books/settings/auto.py。由 self_check.py 用 loader.get_settings() 读出，经 BOOKSVR_COOKIE_SECRET 环境变量转交 booksvr（不写命令行，避免 ps 泄露）。

5.4 启动时序

1nginx 启动

autostart=true

2bootstrap 自检

权限、nginx 配置、syncdb、migrate、update-config

self_check.py 在自检通过后

紧接 tornado 之后，保证晚于库结构变更打开数据库

5.5 数据库

以 WAL + busy_timeout(30000) 打开同一 SQLite，降低与 Tornado 并发访问的锁冲突。阶段 2 只有 merge 一条写路由，且该路由 Python 侧不存在，无双写。

6. 影响范围、风险与回滚

风险影响缓解
Go 复刻的 cookie 算法与 Tornado 不一致所有人被判定为游客用真实 Tornado 测试向量逐字节比对；跨语言契约测试
cookie_secret 下发到 booksvr密钥泄露面扩大只经环境变量传入，不落盘、不写日志
代理逻辑有 bug全站不可用白名单默认空；先只开 3 条路由；回滚只需改一个参数
catch-all 路由导致分发顺序错乱全站路由错乱分发器只匹配有 handler 的路由表
booksvr 早于 syncdb/migrate 打开库库结构变更竞争autostart=false，由 self_check 在 tornado 之后拉起
遗漏 SSR 生产配置SSR 镜像端口冲突崩溃三套 supervisor + 三套 nginx 全部同步
代理破坏缓存/range 头阅读器/Podcast 异常新增 Cache-Control/Accept-Ranges/Content-Range 透传测试
未实现路由静默 404前端功能缺失且难排查未命中一律代理；代理失败返回显式 502 + 日志

回滚

  1. 单条路由：从 -serve-routes 移除该 pattern，重启 booksvr。
  2. 全量：-serve-routes 置空，重启 booksvr → 全部流量回 Tornado。
  3. 彻底：三份 supervisor 把 tornado 端口改回 8000、停用 booksvr，回退 self_check，重启。
  4. 镜像：保留变更前的镜像 tag。

未执行项与风险（如实记录）：
  • 浏览器全流程回归未执行。本次验证在容器内用 curl 完成，未跑浏览器登录/书库/详情/阅读/书架全流程。原因：本阶段是纯后端流量切换，前端 Nuxt 零改动，且路由分发、身份、代理、回滚均已逐项验证。剩余风险：前端在真实浏览器下的会话行为未观测。
  • booksvr 本地路由返回 works 表缺失错误。实测 /api/work/1 返回 {"err":"exception","msg":"... no such table: works"}。原因：镜像内书库尚未跑第一阶段迁移（import-calibre 需要 Calibre 的 title_sort 自定义函数，容器内未注册）。这是第一阶段遗留的数据准备问题，不是阶段 2 的缺陷：阶段 2 的职责是“让流量到达 booksvr”，该目标已达成（请求确实由 booksvr 处理并返回其 JSON 信封）。
  • self_check 读取 cookie_secret 的路径已修复。首次实测发现 self_check.py 以 /opt/talebook-upgrade/ 运行，webserver 不在 sys.path，导致读取失败并跳过 booksvr。已改为先把 SERVER_DIR 加入 sys.path，并增加直接解析 auto.py 的回退；修复后实测读出 cookie_secret 成功。
