用 Go 重写 Calibre 存储层（booksvr）

新增 booksvr/ 作为 Go 实现的书库存储层，采用作品 / 版本 / 格式三层模型：导入默认原地登记源文件（不复制、不改名、不写 OPF），对外保持 Talebook 215 条 HTTP 路由完全兼容，并实现书名与作者名的 8 步自动归一化，把同一本书的不同版次、出版社、格式自动归组到同一作品下。

状态：ACTIVE 创建日期：2026-10-07 所属模块：booksvr 影响范围：booksvr/（新增）、Makefile、Dockerfile、app/pages/admin/imports.vue、app/components/admin/GeneralSettingsContent.vue、app/i18n/locales/*.json、app/test/mock-server.js、webserver/services/media_analysis.py、spec/书籍.md、spec/书库.md、spec/元数据.md、spec/索引.md 需求来源：用户原话（2026-10-07 会话）

1. 原始诉求

“我想把 calibre 重写，保留对外的 api 不变，改为用 go 语言，去掉这个必须重新复制文件的要求，也就是不再要求“文件系统即数据库”，用数据库检索效率明显远超文件系统。另外，也不需要支持 qt 界面，改为使用 web。是否可行？”

“一书多格式是对的！需要保留。而且我还需要实现一书多版本，识别书名，作者名，自动进行归一化。进设计模式完整设计”

“版本：同一本书的不同版次，出版社，格式。作者和书名相同就认为是同一本书，其余不同都是版本差异”

触发背景：Talebook 目前直接依赖 Calibre 的 Python 库与“文件系统即数据库”模型：导入时必须把书复制进书库目录并重命名（books.path 是相对书库根目录的路径，且假定文件就在该目录内），元数据同时写 SQLite 与 metadata.opf 。这带来三个实际问题：

  • 存储冗余：用户已有的电子书目录必须再复制一份，大库下磁盘占用翻倍。
  • 检索效率：以文件系统目录结构为事实来源，检索与归组依赖目录约定而非数据库索引。
  • 依赖沉重：Calibre 转换引擎合计 107,281 行 Python，依赖 Qt 排版引擎与多个 C 扩展；文件名 ASCII 化还引入 32 万行 unihandecode 查表。

已知事实（已实测，非推断）：Talebook 对 Calibre 的依赖面约 30 处 from calibre... import、103 处 self.db / new_api 调用；前端字段契约集中在 webserver/utils.py:66-170 的约 25 个字段；格式转换已经是外部进程调用（webserver/services/convert.py:158 的 subprocess.Popen(["ebook-convert", ...])），因此转换引擎与存储层天然解耦。

为什么现在处理：Talebook 已经在“对抗” Calibre 存储模型（monkey-patch 路径构造函数、直接 SQL 绕过 Calibre API），说明“摆脱文件系统即数据库”是已被实践证实的刚需，而非新增偏好。

2. 目标与边界

目标

  • booksvr/ 目录存在，go build ./... 通过；单二进制 + embed 前端可部署。
  • 导入默认原地登记源文件：不复制、不改名、不写 OPF；导入后源文件位置与文件名完全不变。
  • 实现作品 → 版本 → 格式三层模型；《三体》4 个文件导入后为 1 work / 3 book / 4 format。
  • 实现书名与作者名的 8 步归一化流水线，每步有独立单元测试，internal/normalize 覆盖率 ≥ 90%。
  • 对外保持 Talebook 215 条 HTTP 路由的路径、方法、响应结构与 Python 版逐字段一致。
  • 前端 Nuxt 除多目录 UI 外零改动可跑通登录、书库、详情、阅读、书架全流程。
  • 提供 Calibre 单向只读迁移（幂等、源库不被修改）与全库归一化重算命令。
  • 必须保持的不变量：books.id 语义不变（仍是一本书 = 一个版本）；{"err": "ok", ...} 响应信封不变；files[] 结构不变。

非目标

  • 不实现 Calibre 桌面版 GUI 的任何功能；不提供 Qt 界面。
  • 不导出回 Calibre 格式，不保证 Calibre 桌面版能继续打开新书库。
  • 不做全书正文全文检索（超大库不可承受），仅做元数据检索（trigram 分词，支持中文子串）。
  • 不重写 Calibre 的 107,281 行转换引擎；只做读取主流格式 + 单向转 EPUB。
  • 不引入 32 万行 unihandecode 式的文件名 ASCII 化查表；繁简表限制在 3000-5000 字。
  • 本轮不实现归一化算法升级后的自动后台重算（只提供手动命令）。
  • 不修改前端 Nuxt 代码（多目录 UI 为唯一例外，见第 5 节）。
  • 不重构与本次目标无关的 webserver/ 代码。
  • 后续事项：详情页“其他版本”区块与合并按钮消费新增的 work/versions/merge 接口；触发条件为下一轮前端迭代。

5. 方案

方案结论：新增 booksvr/ 作为 Go 实现的书库存储层，采用作品 → 版本 → 格式三层模型。所有权划分：works 表拥有作品层（归一化后的书名 + 作者），books 表保留为版本层（books.id 语义不变），book_formats 表拥有格式层（绝对路径，不复制不改名）。数据流：导入 → 8 步归一化 → work_key 命中作品 → edition_key 命中版本 → 同版本加格式。失败表现：空 edition_key 不自动合并，各自成版本；同一 book 重复导入同一 format 返回现有 samebook 语义。这是最小完整方案，因为 books.id 不变使 215 条路由与前端契约完全不受影响，works 是纯增量聚合层，回滚只需停止使用新表。

5.1 三层数据模型

-- 第 1 层：作品（新增）
CREATE TABLE works (
    id             INTEGER PRIMARY KEY,
    title_norm     TEXT NOT NULL,          -- 归一化书名（已剔除版本后缀）
    author_norm    TEXT NOT NULL,          -- 归一化作者
    work_key       TEXT NOT NULL UNIQUE,   -- title_norm + '\x1f' + author_norm
    display_title  TEXT NOT NULL,
    display_author TEXT NOT NULL,
    created_at     INTEGER NOT NULL,
    updated_at     INTEGER NOT NULL
);
CREATE INDEX idx_works_title_norm  ON works(title_norm);
CREATE INDEX idx_works_author_norm ON works(author_norm);

-- 第 2 层：版本（复用 books 表，新增列）
ALTER TABLE books ADD COLUMN work_id     INTEGER REFERENCES works(id);
ALTER TABLE books ADD COLUMN edition_key TEXT;   -- 版本指纹
ALTER TABLE books ADD COLUMN title_norm  TEXT;
ALTER TABLE books ADD COLUMN author_norm TEXT;
CREATE INDEX idx_books_work_id     ON books(work_id);
CREATE INDEX idx_books_edition_key ON books(work_id, edition_key);

-- 第 3 层：格式（新增）
CREATE TABLE book_formats (
    id      INTEGER PRIMARY KEY,
    book_id INTEGER NOT NULL REFERENCES books(id) ON DELETE CASCADE,
    format  TEXT NOT NULL,
    path    TEXT NOT NULL,        -- 绝对路径，不复制不改名
    size    INTEGER NOT NULL,
    mtime   INTEGER NOT NULL,
    hash    TEXT,
    UNIQUE(book_id, format)
);

关键语义：work_key = title_norm + '\x1f' + author_norm 决定“是不是同一本书”；edition_key = norm(出版社) + '\x1f' + norm(版次/年份) + '\x1f' + norm(译者) 决定“是不是同一版本”。《三体》4 个文件 → 1 work / 3 book / 4 format。

5.2 八步归一化流水线

输入 "《三体》（第二版） 刘慈欣 著"
  ↓ 1. 去盗版站后缀    remove_zlibrary_suffix 等价实现
  ↓ 2. 全半角统一      ＡＢＣ→ABC，１２３→123
  ↓ 3. 空白归一        去零宽字符 U+200B/U+FEFF
  ↓ 4. 标点归一        去《》「」【】、去副标题分隔符
  ↓ 5. 繁简统一        内置对照表（embed，约 20-50 KB）
  ↓ 6. 大小写统一      casefold
  ↓ 7. 去版本后缀      → 提取而非删除
  ↓ 8. 作者归一        去「著/编/译」、统一姓名顺序
输出 title_norm="三体"  author_norm="刘慈欣"  suffixes=["第二版"]

第 7 步关键设计（提取而非删除）：

type SuffixParse struct {
    Core     string   // "三体"      → 进 title_norm
    Suffixes []string // ["第二版"]  → 进 edition_key
}

《三体全集》→ Core="三体", Suffixes=["全集"]：归入同作品但不是同一版本。若直接删除后缀，《三体全集》会被误合并进《三体》的同一版本。误合并兜底：edition_key 为空时不自动合并，各自成版本。

5.3 导入与归组流程

Input扫描 / 上传源文件

解析元数据，得到书名、作者、出版社、版次、译者

Guard8 步归一化

算出 work_key 与 edition_key；空指纹不合并

Core三层归组

work_key 命中？→ 否则新建 work；edition_key 命中？→ 否则新建 book；同 book 已有该 format？→ 否则加 format

Output原地登记

对外行为保持不变：{"err": "samebook"}、add_format、import_book 的语义与响应结构与 Python 版一致，前端零改动。

5.4 存储层：去掉「文件系统即数据库」

维度旧（Calibre）新（Go）
文件位置books.path = 相对书库根目录book_formats.path = 绝对路径
文件名ASCII 化（32 万行 unicode 表）保留原始文件名，删除查表
导入必须复制 + 改名默认原地登记，不复制不改名
目录约定data/{author}/{title}/{id}/无目录约定，路径即事实
封面cover.jpg 在书目录内covers/{book_id}.jpg 独立目录
元数据SQLite + metadata.opf 双写仅数据库，导出时按需生成 OPF

兼容层：books.path 字段保留（存第一个格式所在目录），供 webserver/main.py:177-191 的 monkey-patch 与 webserver/services/external_index.py:74-75 的直接 SQL 平滑迁移，避免一次性改动面过大。

5.5 HTTP 层与新增接口

215 条既有路由全部保留，路径、方法、响应结构不变。新增 3 条路由，遵循仓库 RESTful 规范（单数资源名、动作作为子路径）：

方法路径用途响应要点
GET/api/work/([0-9]+)作品详情作品元数据 + 版本列表 + 每版本格式列表
GET/api/book/([0-9]+)/versions同作品其他版本同 work_id 下其他 book_id 的摘要
POST/api/book/([0-9]+)/merge人工合并版本把目标书并入当前书所在作品；返回合并结果

前端如何使用（关键设计）：前提是前端 Nuxt 除多目录 UI 外零改动，因此新增的 work/versions/merge 接口不被现有前端调用，而是作为后续前端迭代的接口储备。书库列表、详情页、下载弹窗、格式转换、阅读/书架/笔记全部继续挂 book_id，不介入；「同作品其他版本」是新增接口的唯一消费者。

为什么本轮不接入前端：用户要求「前端 Nuxt 零改动」。若本轮同时接入，会破坏「215 条路由完全兼容」的验收口径，也无法用「前端零改动跑通」作为兼容性的强证据。

后续前端接入路径（不在本轮范围，仅记录以便接口设计不返工）：

  1. 在 app/pages/book/[bid]/index.vue 详情页新增「其他版本」区块，调用 $backend('/book/' + bid + '/versions')。
  2. 用 app/components/BookCards_Small.vue 渲染版本列表（它已支持 href 与 id，可直接复用）。
  3. 版本卡片点击跳 /book/{version.id}，复用现有详情页路由。
  4. 管理员在详情页提供「合并到当前作品」按钮，调用 POST /api/book/{id}/merge。
  5. 新增 i18n 文案到 app/i18n/locales/*.json，注意禁止字面量 @ 与 <。

关键决策

决策点选择理由放弃项
作品层与现有 API 关系保留 books 表作为版本层，新增 works 表作为作品层books.id 语义不变，215 条路由与前端契约完全不受影响；works 是纯增量聚合层；回滚只需停止使用新表彻底重建 works/editions/formats 三张新表、books 仅作兼容视图（所有以 book_id 为键的路由、阅读进度、笔记、书架都要重新映射，与「前端零改动」硬约束冲突）
版本与格式层级作品 → 版本 → 格式（三层）同一版次的 epub+mobi 合并为 1 个版本，版本内再列格式，符合用户对「版本」的定义作品 → 版本(=文件) 两层（同一版次的 epub+mobi 会显示成 2 个版本，用户会觉得「版本」一词被滥用）
同版本判定依据按「版本指纹」自动判定：edition_key = norm(出版社) + '\x1f' + norm(版次/年份) + '\x1f' + norm(译者)归一化后相同即同一版本，无需人工介入人工指定版本（大库不可行）
版本后缀处理提取而非删除：后缀进 edition_key避免《三体全集》被误合并为《三体》同一版本直接删除后缀（会造成误合并）
空指纹处理不自动合并，各自成版本数据安全优先于自动化程度；误合并比漏合并代价高空指纹也合并（误合并风险不可控）
归一化键计算时机写入时持久化 + 提供全库重算命令检索走索引，性能可控；规则升级时可手动重算查询时实时计算（大库不可承受）；不做后台自动重算（本轮范围外）
繁简统一实现内置精简对照表（3000-5000 字，单文件 embed）零依赖、约 20-50 KB、可离线OpenCC Go 移植库（引入数 MB 词典依赖）；不做繁简归一（「三體」与「三体」仍是两本书）
全文检索范围仅元数据，trigram 分词（支持中文子串）超大库可承受全书正文 FTS（1 万本约 15-20 GB）
多目录配置复用现有 import_allowed_roots，不新增配置项后端已支持，只缺前端 UI新增独立的多书库根目录配置（重复造轮子）
兼容策略215 条路由路径、方法、响应结构不变；books.path 字段保留作兼容层前端零改动是硬验收口径不接受任何隐式降级（如静默改变 files[] 结构）

6. 影响范围、风险与回滚

影响范围

新增：booksvr/ 整个目录（Go 模块、internal/normalize、internal/library、internal/migrate、internal/httpapi、internal/reindex、docs/route-inventory.md）。

修改：Makefile（新增 build-go/test-go/lint-go）；Dockerfile（多阶段构建）；webserver/services/media_analysis.py（新增 DOCX/FB2/HTMLZ）；app/pages/admin/imports.vue、app/components/admin/GeneralSettingsContent.vue、app/i18n/locales/zh-CN.json、app/i18n/locales/en-US.json、app/test/mock-server.js。

数据：新增 works、book_formats 两张表；books 表新增 work_id/edition_key/title_norm/author_norm 四列与两个索引。

接口：215 条既有路由不变；新增 3 条（/api/work/{id}、/api/book/{id}/versions、/api/book/{id}/merge）。

配置：不新增配置项；复用 import_allowed_roots。

涉及的 spec/ 篇目（改变产品行为，必须同 PR 更新）：spec/书籍.md（一书多格式、一书多版本、新格式与不可在线阅读边界）、spec/书库.md（导入不再复制文件的领域规则）、spec/元数据.md（归一化与作品归组规则）、spec/索引.md（若新增篇目则同步收录）。

保持不变

  • books.id 语义：仍是一本书（一个版本），不得把作品层语义混入 book_id。
  • 215 条路由的路径、方法、响应结构；{"err": "ok", ...} 信封。
  • files[] 逐项结构（format/size/href/online_readable）。
  • {"err": "samebook"}、add_format、import_book 的对外语义。
  • OPDS、WebDAV、多用户与权限能力。
  • 格式转换仍走外部进程，不重写转换引擎。
  • books.path 字段保留作兼容层，供现有 monkey-patch 与直接 SQL 平滑迁移。
主要风险：
  • 误合并（最高风险）：归一化过激会把不同书合并到同一作品。触发条件：书名归一化过度（如把副标题当版本后缀剔除）。监控：迁移报告输出「被合并数」与「空指纹数」；reindex-normalize 输出差异报告。缓解：版本后缀提取而非删除；空 edition_key 不自动合并；保留人工纠正（POST /api/book/{id}/merge）。
  • 路由键依赖（已发生，已决策）：实施项 1 盘点发现 22 条路由以 books.path 家族（fmt_<format> 路径键）为键，已触发停止条件并上报。用户决策：方案 C —— 逐路由改造，把 22 条路由改为直接查 book_formats，同步修改 webserver/ 侧代码。监控：契约测试逐字段对比 215 条路由响应结构。缓解：逐条核对路径语义假设；完整清单见 booksvr/docs/route-inventory.md。
  • 版本指纹缺失率过高：真实书库中出版社/版次/译者大量为空，导致自动归组收益不足。触发条件：迁移报告中空指纹占比过高。监控：迁移报告。缓解：回到设计确认，不自行扩大归一化范围。
  • 契约测试发现无法兼容的路由：触发条件：实施项 11 逐字段对比失败。缓解：停止并说明，不静默改变响应结构。
  • 前端范围越界：发现必须改多目录 UI 以外的前端文件才能兼容。缓解：停止并说明，不扩大例外范围。
  • 繁简表覆盖不足：生僻字不转换，导致部分书未归组。缓解：表限制在 3000-5000 常用字，接受漏合并（比误合并安全）；后续可通过 reindex-normalize 重算。
回滚：代码层面，booksvr/ 是新增目录，删除即可；Makefile/Dockerfile 改动可单独回退。数据层面，works 与 book_formats 是新增表，books 新增的四列均为可空，旧代码不读它们即可继续工作，因此无需数据迁移即可回滚；如需彻底清理，删除两张新表与四个新列即可。前端多目录 UI 回退到单个 scan_upload_path 文本框，后端 import_allowed_roots 数组仍兼容单值。Calibre 迁移是单向只读，源库不被修改，回滚无副作用。
